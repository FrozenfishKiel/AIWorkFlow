# AI内容生产与运营工作流系统项目需求与环境准备方案

这份文档有两个用途。

第一个用途，是把这个项目到底要做什么、做到什么程度、哪些该做、哪些先不做，一次性说清楚。这样后面不管是开新对话继续推进，还是自己回头看，都不会再因为边界发散把项目做歪。

第二个用途，是把当前机器环境到底缺什么、哪些技术是干什么用的、没装的话该怎么补，提前说透。这样后面正式开工时，不会一上来就卡在环境问题上。

这份文档默认服务的是项目第一阶段，也就是第一版可上线原型。这里的“可上线”，不是指把页面跑起来就算完，而是指它已经具备完整主链路，能让真实用户开始试用。

## 零、项目命名与产品身份

这个项目既然目标是做成可上线标准，而不是只做一个本地演示原型，那它就不能一直停留在“那个 AI 项目”“那个内容 Agent”这种临时叫法上。项目名本身虽然不决定技术质量，但它会直接影响后续几件事：

- 你怎么对外介绍这个项目
- 你怎么写简历和项目经历
- 你怎么在文档里统一称呼它
- 你怎么让后续参与开发的 AI 理解“它到底是个产品，还是个玩具”

所以这份方案先把项目名正式定下来。

统一项目名称：

`AI内容生产与运营工作流系统`

这个名字比前一版更像人话，也更贴近你资料里那些真实项目的叫法。面经和项目画像里常见的命名，基本都是这种风格：

- `企业知识库问答系统`
- `文档处理 / 翻译 Agent`
- `研发辅助 Agent`
- `工作流型 Agent 平台`

它们有一个共同点，就是不追求品牌感，也不追求好听，而是直接把“做什么”写进项目名里。因为面试和项目沟通时，最重要的是让别人一眼知道这是个什么系统。

按这个标准来看，我们这个项目最稳的名字，就是把核心功能直接说出来。

这个项目的核心功能不是聊天，也不是通用平台，而是：

- 处理内容输入
- 做内容理解
- 调用业务知识做 RAG 参考
- 生成内容工作流结果
- 支持结果回看、人工介入和导出

所以最合适的命名方式，就是突出：

`内容分析 + 运营 + 工作流 + 系统`

这里我把“内容运营”补成“内容生产与运营”，原因是它更像人话，也更贴近我们现在真正要做的事。

这个项目不是直接替人发内容，也不是单纯写文案。它前半段其实花了很大力气在做：

- 内容输入后的理解
- 重点提炼
- 参考资料召回
- 工作流组织

这些都更接近“分析”而不是“执行”。如果名字里只写“内容运营”，会有点像后半段动作很重、前半段理解很轻；但我们的系统恰恰相反，真正的价值很大一部分在前半段。

“内容生产”这几个字，既能覆盖前半段的内容理解、参考召回、结构化生成，也不会像“内容分析”那样偏术语化；“内容运营”则保留了项目的业务落点，所以这个名字更适合作为简历项目名、需求文档名和后续统一称呼。

所以最终保留一个名字就够了：

`AI内容生产与运营工作流系统`

后续所有文档、对话、需求、简历项目描述里，都统一只用这一个名字，不再拆主名、副标题和简称，避免混乱。

## 一、项目到底是什么

这个项目不是一个泛化的 Agent 平台，也不是一个什么都能接、什么都能做的 AI 工作台。它更像一个面向内容团队的业务型 AI 应用。

它要解决的不是“写不出文案”这么单一的问题，而是内容团队在处理外部文章、活动资料、品牌文档、行业参考内容时，前置准备太重、参考资料分散、口径不统一、步骤依赖经验、结果不好复用这些更实际的问题。

所以这个项目真正要做的事情是：把内容先吃进来，先理解，再结合团队已有的业务知识做参考召回，然后把结果组织成一套可回看、可修改、可导出的内容工作流产物。

用一句更直白的话说，这个产品卖的不是“我替你自动发内容”，而是“我先帮你把内容任务前半段最耗时间、最容易乱的部分做顺”。

## 二、为什么做，目标是什么

这个项目的目标不是为了追新技术，也不是为了把 RAG、Agent、多模态这些词都堆进去。它的目标很现实，就是做一个看起来像产品、用起来有闭环、技术上也讲得清的 AI 应用开发项目。

第一阶段的目标有三个。

第一，是把这条主链路完整打通：

`内容输入 -> 内容理解与抽取 -> RAG 检索参考 -> 工作流生成 -> 稳定快照 -> 结果导出`

第二，是把 RAG 做成真正有业务价值的能力。它不是一个附属组件，也不是“接个向量库意思一下”。它要承担的是品牌口径约束、历史内容参考、平台规则引用、产品资料补充这些真正影响生成质量的事情。

第三，是把可见性和可追溯性放在主链路中心，而不是把系统做成一个黑盒。这个项目最终要体现出来的，不是“AI 自己干完了”，而是“AI 先做一轮结构化处理，并把风险、证据和待确认项完整暴露给人回看”。

## 三、第一阶段最后要做成什么样

第一阶段交付出来的，不应该是一个平台底座，而应该是一个内容运营工作台。

用户进入系统以后，至少应该能完成下面这些动作：

1. 新建一个内容任务。
2. 输入一个 URL、粘贴一段文本，或者上传一份文档。
3. 查看系统对这份内容的理解结果，比如摘要、主题、重点、受众、风险点、可复用素材等。
4. 查看系统从业务知识里检索到的参考资料，以及为什么命中这些资料。
5. 查看系统生成的内容工作流结果，包括拆解建议、角度建议、改写建议、待确认项等。
6. 查看风险、证据和待确认项，必要时自行修改或重新生成。
7. 最后把结果导出给下游继续使用。

所以第一阶段最后的样子，应该是一个围绕单次内容任务运转的工作台，而不是一个抽象能力展示页。

## 四、项目边界

这部分最重要。因为这个项目最容易出的问题，不是做不出来，而是越做越大，最后边界糊掉。

### 4.1 这一阶段必须要做的

第一阶段必须围绕单次内容任务闭环展开。换句话说，系统至少要能稳定完成这几件事：

- 接内容
- 读内容
- 理内容
- 找参考
- 生成结果
- 让结果可回看、可介入
- 把结果导出去

这里的关键词是“单任务闭环”和“结果可回看、可追溯”。

### 4.2 这一阶段明确不做的

有些东西不是没价值，而是不该在第一阶段碰。

第一，不做自动发布。
这版不直接连接公众号、小红书、视频号、CMS 或任何外部发布端。第一阶段的重点是生成、回看和导出，不是投放。

第二，不做重爬虫。
不做整站抓取，不做全网采集，不做定时批量扫站。URL 输入只处理用户明确提交的单个页面，或者我们支持范围内的公开内容页面。

第三，不做多 Agent 平台化。
不做角色市场、工具市场、任意编排中心，不做“搭积木式”开放工作流平台。

第四，不做 MCP。
MCP 很重要，但它不是这个项目第一阶段成立的前提。这个阶段优先保证业务闭环，而不是工具协议标准化。

第五，不做多租户、计费和复杂权限。
第一阶段不是商业化平台，不做套餐、组织权限、团队空间隔离这些重基础设施。

第六，不做 GraphRAG 和重型知识治理。
这版 RAG 是业务型 RAG，不是知识平台。

### 4.3 关于视觉内容提取的边界

第一阶段保留视觉内容提取能力，但不单独建设一条传统 OCR 产品线。

意思是，这个系统可以支持图片型文档、扫描件、截图这类内容进入后续流程，但这项能力的定位，是服务内容理解，不是做一个独立 OCR 系统，更不是把项目主线讲成“识别准确率竞赛”。

## 五、用户和客户怎么用

这个项目第一阶段服务的，不是算法团队，也不是要搭平台的中后台团队，而是直接做内容生产和内容运营的人。

典型用户包括：

- 内容运营
- 编辑
- 品牌内容负责人
- 增长内容人员
- 负责最后把关的内容负责人

他们的使用方式应该很朴素。

用户拿到一篇外部文章、一个活动链接、一份品牌文档，或者一段需要处理的文本，把内容送进系统。系统先帮他读一遍，告诉他这是什么、重点是什么、哪些内容值得提炼、它和已有业务资料里哪些内容相关。接着，系统再给出这次任务建议怎么做，需要参考哪些历史内容、哪些地方必须人工判断、哪些输出可以直接继续编辑。最后由内容人员自己回看、必要时修改、定稿和导出。

所以从用户视角看，这个产品不是一个“神奇 AI”，而是一个把准备工作、参考归并和流程组织提前做好了的内容工作台。

## 六、按真实使用流程拆功能

### 6.1 内容输入

系统第一阶段支持三类输入：

- URL
- 粘贴文本
- 上传文档

URL 主要用于外部网页、公开文章页、产品页、文档页这类内容。粘贴文本适合临时处理一段内容。上传文档主要服务活动资料、品牌说明、会议纪要、PDF、Word 这类文件。

这一层要解决的问题，不是“输入来源越多越好”，而是“把高频输入稳定吃进去”。

这里还要额外明确一个边界：`URL 只是输入方式之一，不是唯一主入口`。原因很现实，很多真实网页会碰到登录态、反爬、动态渲染、区域限制、评论区异步加载、平台策略限制这些问题。如果把项目主价值全部压在 URL 解析上，工期会非常容易失控。

所以第一阶段要把输入优先级定清楚：

- `第一优先级`：粘贴文本
- `第二优先级`：上传文档
- `第三优先级`：公开网页 URL

也就是说，就算某些 URL 最后不稳定，这个产品依然必须能靠“文本粘贴 + 文档上传”完成大部分核心业务链路，不能因为网页抓取受限就让整条链路失效。

### 6.2 内容解析与理解

系统收到内容后，要先做基础解析，再做业务可用的结构化理解。

第一阶段至少要输出这些内容：

- 标题
- 摘要
- 主题
- 核心观点
- 关键信息点
- 可能的目标受众
- 可复用素材片段
- 潜在风险点
- 不确定项

这一步如果做不稳，后面的 RAG、工作流和结果回看都会漂，所以它必须做扎实。

### 6.3 业务型 RAG 检索

系统不是去网上泛搜，而是在用户当前任务所选的业务知识范围里做检索。

这部分知识优先来自内容团队自己的资产，比如：

- 品牌语气和写作规范
- 历史优稿和爆文样本
- 产品资料
- 平台规则
- 活动说明
- 常见问答
- 审核标准

这一层最关键的要求，不是“能搜到点东西”，而是：

- 检索结果可展示
- 引用来源可追溯
- 命中理由讲得清楚

用户要能知道系统参考了什么，而不是只看到一个结果。

### 6.4 工作流生成

这里的“工作流”不能写虚。

第一阶段它不是一个开放式规划器，而是一组围绕内容任务的结构化执行建议。比如：

- 内容拆解
- 参考对照
- 角度建议
- 改写任务
- 风险检查
- 输出模板建议
- 待人工确认项

换句话说，它生成的不是一段看起来很聪明的话，而是一套可以继续处理的工作结果。

### 6.5 结果回看与人工介入

第一阶段保留人工介入能力，但不再把它设计成“所有任务都必须人工放行”的主链硬门。

用户至少要能：

- 查看抽取结果
- 查看风险点、不确定项和证据使用
- 必要时修改工作流结果
- 记录问题并决定是否重新生成
- 基于稳定快照继续导出

如果要支持重跑，也应该尽量基于已知问题重算，而不是每次全链路黑盒重来。

### 6.6 结果导出

导出的重点不是格式炫不炫，而是能不能顺利进入下游流程。

第一阶段至少支持：

- 复制富文本
- Markdown 导出
- 结构化文本导出

如果后面业务需要，可以再补 Word 或 PDF 导出，但这不该成为第一阶段主卖点。

## 七、第一阶段必须做扎实的东西

有些能力可以先收窄范围，但不能做浅。

### 7.1 内容理解与结构化抽取

这是后面所有能力的地基。抽取得不稳，检索会偏，生成会飘，审核会痛苦。

### 7.2 业务型 RAG

RAG 这一块不能做弱。

这里说的“做扎实”，不是上很多花哨检索链路，而是把下面这些事情认真做好：

- 知识范围定义
- 文档接入与清洗
- chunk 切分
- metadata 设计
- embedding 检索
- 召回质量
- 引用展示
- 可追溯性

也就是说，RAG 要做得窄，但不能做得糙。

### 7.3 工作流生成的可控性

工作流生成结果必须围绕真实内容任务，步骤清楚、边界清楚、待确认项清楚，不能变成空泛建议。

### 7.4 结果回看与人工介入体验

结果页必须好用，能看、能查证、能重新生成、能导出。对真实内容团队来说，这层的体验比“模型说得多聪明”更重要。

## 八、第一阶段先不纳入的内容

为了保证工期和边界，这些内容明确延后：

- 多 Agent 管理
- 通用流程编排中心
- 工具协议开放
- GraphRAG
- 跨域通用知识大底座
- 自动发布和自动投放
- 站点级重型抓取
- 批量全网采集
- 多租户
- 计费
- 套餐
- 复杂组织权限
- 单独的传统 OCR 技术线

## 九、技术栈，以及每个技术分别负责什么

第一阶段技术栈要遵循一个原则：够稳、够快、够容易收口。

### 9.1 前端

`React` 是前端 UI 库，负责页面和交互本身。  
`Next.js` 是基于 React 的全栈框架，自带路由、构建和一部分服务端能力。

对这个项目来说，前端主要负责：

- 任务创建页
- 内容理解结果展示
- RAG 参考结果展示
- 工作流结果展示
- 结果回看与人工介入
- 结果导出交互

如果第一阶段追求尽快开工，我更推荐：

`React + Vite`

原因很简单：这版后端已经明确会用 FastAPI，前端没必要一开始就引入 Next.js 的额外全栈能力。React + Vite 更轻，边界也更清楚。

如果后面确定需要更强的前后端一体化能力，再切到 Next.js 也不晚。

### 9.2 后端

`FastAPI` 负责整个后端 API 层。

它在这个项目里的职责很明确：

- 任务创建接口
- 文件上传接口
- 任务查询接口
- 任务详情与导出接口
- 导出接口
- 调用工作流和模型服务的统一入口

它不是可选项，而是第一阶段后端主力。

### 9.3 工作流编排

`LangGraph` 负责单 Agent 工作流编排和状态管理。

它在这个项目里不是拿来炫技的，而是承接这种有状态流程：

`理解 -> 检索 -> 生成 -> 稳定快照 -> 导出`

第一阶段只把它当运行时，不把它做成开放平台。

### 9.4 数据库

`PostgreSQL` 负责主业务数据存储。

主要包括：

- 任务记录
- 稳定快照与导出记录
- 知识库元数据
- 引用关系
- 导出记录

`pgvector` 负责向量检索能力。它和 PostgreSQL 放在一起，适合第一阶段把结构化数据和向量数据统一放在一个系统里管理。

### 9.5 缓存和异步

`Redis` 负责缓存、短期状态和任务中间态加速。

`Celery` 负责异步任务处理，比如：

- 文档解析
- 向量化入库
- 批量检索
- 导出生成

它们不一定要在第一天就全部装好，但从架构上要提前给它们留位置。

### 9.6 内容解析

`Unstructured` 负责 URL、HTML、PDF、Word 这类内容的解析与预处理。

它的职责不是“帮你做一切”，而是让内容先变成后面工作流能用的结构。

### 9.7 文件存储

`S3 兼容对象存储` 负责原始上传文件、解析中间产物和导出文件的保存。

第一阶段如果不想本地先搭完整对象存储，也可以先用简化方案，但从设计上最好按对象存储来考虑。

### 9.8 模型服务

`LLM + Embedding 模型服务` 负责：

- 内容理解
- 结构化抽取
- 工作流生成
- 向量化

这里要强调的是“可替换”，但第一阶段不需要做复杂模型路由平台。

第一阶段默认模型路线也要明确下来，不然后面开发时很容易反复改接口。

模型优先级按当前要求排序是：

- 稳定性
- 多模态能力
- 部署难度
- 成本

按这个标准，如果完全不考虑当前网络环境和演示成本，第一阶段默认主模型本来会更偏向 OpenAI。

但这份方案最后服务的是你当前这条实际路线：`低成本、可演示、可面试优先`，而不是“先按海外生产环境堆最稳模型”。

所以最终定稿为：

- `第一阶段默认优先接 DeepSeek 或你当前能稳定调用的兼容 API`
- `工程上保留 OpenAI 兼容接入位`

这样定的原因不是说 OpenAI 不好，而是它在你的当前环境下，会额外引入地区支持、访问链路和演示稳定性的不确定性。对第一阶段来说，这些不确定性不值得优先承担。

OpenAI 在这个项目里的定位，调整为：

- 多模态和高质量能力的后续增强路线
- 后续可切换的兼容模型提供商
- 当网络和接入条件允许时的升级选择

所以工程上要做到的是：

- 上层工作流不要直接绑死某一家模型 SDK
- 模型调用层要做成统一封装
- Prompt 输入输出协议尽量统一
- 结构化输出要走固定 schema

这样后面即使从 DeepSeek 切到 OpenAI，或者同时保留两条路线，改动范围也不会失控。

### 9.9 可观测性

`LangSmith` 或同类 LLM 可观测方案，负责链路 tracing、问题排查、Prompt 调试和质量评估。

它不是锦上添花。只要你要认真调 RAG 和工作流，就迟早会需要这层东西。

### 9.10 部署与云端基础设施

这部分必须补清楚，因为你当前对“部署”几乎没有概念，而这个项目又明确要按上线标准来做。

先用人话解释几个词：

- `部署`：就是把项目从你自己电脑里，放到别人也能访问的线上环境里
- `云服务器`：就是租一台远程电脑，你可以把前端、后端、数据库都自己装上去运行
- `托管平台`：就是别人帮你把很多运维细节包掉，你主要管代码和配置

第一阶段最常见的几个选择分别是：

- `Vercel`：偏前端和 Web 应用托管，特别适合部署 React / Next.js 这类前端项目
- `Railway`：偏全栈托管，比较适合直接部署 FastAPI、后台服务和附属服务
- `Supabase`：本质上是云端 Postgres 平台，同时附带存储、鉴权、向量能力等配套能力
- `云服务器`：自由度最高，但部署、环境、进程、数据库、安全和运维都更需要自己管

如果继续用人话区分，它们大概是这样：

- `Vercel` 更像“帮你托管网站前台”
- `Railway` 更像“帮你托管后端服务和运行环境”
- `Supabase` 更像“帮你托管数据库和对象存储这类底座”
- `云服务器` 更像“给你一台裸机器，你自己装一切”

对你当前阶段来说，第一版不建议一上来就走纯云服务器。不是不能上，而是它会额外引入很多和 AI 应用本身无关的运维学习成本。

所以第一阶段默认部署建议直接定成：

- `前端：Vercel`
- `后端：Railway`
- `数据库与对象存储：Supabase`

这套组合的好处是：

- 前后端职责分离清楚
- 上手门槛相对低
- 比纯云服务器更省运维
- 已经足够支持第一阶段上线
- 后面如果要迁移到自建云服务器，也不是推倒重来

这里也要明确一点：`部署难度` 和 `开发难度` 不是一回事。你本地依然可以先用最小环境开发，等主链路稳定后再接入这套云端部署方案。

但这套部署方案的定位也要写死，避免后面误判：

`它是第一阶段的低成本演示部署方案，不承诺中国内地生产级稳定访问。`

也就是说，这一版的目标是：

- 方便你尽快把项目真正上线
- 方便你生成可访问链接
- 方便你做作品展示和面试演示
- 尽量降低备案、服务器采购和运维投入

它不是这一阶段要解决的问题：

- 中国内地任意网络环境下的强稳定访问
- 大规模正式商用部署
- 严格的国内生产合规上线

因此，第一阶段还要同步接受几条现实约束：

- 面试官和你自己访问时，可能会受到网络环境影响
- 一定要绑定自定义域名，不要把 `.vercel.app` 当成正式展示地址
- 要尽量减少前端对海外第三方脚本、字体和资源的依赖
- 最好额外准备录屏演示和截图兜底，避免面试当天网络波动影响展示

## 十、上线标准

第一阶段能不能算上线，不能按“演示跑通了”判断，而要按“真实团队能不能开始用”判断。

这里的“上线”也不能只理解成把前后端部署出去。对一个程序员来说，如果一个项目只是页面能打开、接口能返回，但没有命名、没有边界、没有审核链路、没有错误处理、没有基础可观测性，那其实还不能叫负责任地上线。

但这份方案到这里也要正式定稿一件事：

`第一阶段的上线目标，定义为可演示上线，而不是正式商用上线。`

这句话很重要。它的意思不是“随便做个 demo 就算完”，而是：

- 要有真实可访问地址
- 要能跑通核心业务链路
- 要能让别人实际打开、看到、操作和理解这个系统
- 要能支撑你做项目展示、面试演示和项目讲解

但它暂时不要求：

- 中国内地生产级稳定访问
- 长期正式商用运营
- 备案、计费、多租户和复杂运维体系

所以这版项目追求的是：`像一个真的业务系统一样被做出来，并且能被演示使用`，而不是第一阶段就把它做成完整商业化产品。

至少要满足这些条件：

- 三类输入方式都能稳定使用
- 常见 URL、纯文本、PDF/Word 文档都有可接受成功率
- 至少有一个明确业务知识域已经建好
- RAG 检索结果可展示来源和引用片段
- 工作流结果是结构化、可编辑、可回看的，不是散文式回答
- 稳定快照、证据和处理轨迹完整可见，并支持继续导出
- 全链路有基础状态可见性，用户知道任务卡在哪一步
- 用真实样本测试时，大部分任务都能产出“可继续人工编辑”的结果
- 每次任务都能追踪输入、检索参考、生成结果、人工修改和导出记录

除此之外，还要补几条更像真正产品的上线标准：

- 项目有稳定名称，对内对外说法统一，不再是临时项目代号
- 有明确支持范围，尤其是 URL 输入范围、文档类型范围、知识域范围，不能让用户误以为它是万能抓取器
- 有失败兜底策略，至少能提示失败原因、失败阶段，以及下一步建议
- 有基础日志和链路追踪，出了问题能知道是输入解析、RAG、生成还是导出卡住
- 有最基本的数据边界意识，至少能说清楚用户上传内容、知识库资料和导出结果分别存在哪里
- 有最基本的部署说明，别人接手时知道怎么把它跑起来，而不是只有作者自己知道
- 有最基本的产品文档，后续不管是开发 AI、你自己还是面试官，都能看懂它的主链路和技术职责
- 有最基本的任务审计能力，至少能回看某次任务用了什么输入、命中了哪些参考、最后导出了什么

如果要更具体一点，第一阶段建议用 30 到 50 个真实任务样本做内部验收，重点看：

- 任务跑通率
- RAG 命中有效率
- 结果可继续编辑率
- 导出成功率

这里不追求一步到位的极限效果，但必须追求“能开始内部试用”。

## 十一、除了开发文档，还必须补哪些“解释型文档”

这个项目最后是要拿去找工作的，而你现在对里面很多技术栈还不熟。所以这里必须额外加一层要求：

`项目相关文档不能只为开发服务，还必须为学习、复盘和面试讲解服务。`

原因很简单。AI 应用开发岗位在面试里，项目不会只问“你用了什么”，而是会继续追问：

- 这个技术为什么放在这里
- 它在项目里到底负责什么
- 为什么不用别的方案
- 它和前后模块怎么衔接
- 它出问题的时候，问题通常出在哪

如果这些东西你自己说不清，那项目哪怕做出来了，面试里也会很被动。

所以这个项目从第一阶段开始，就必须同步沉淀一套“解释型文档”。注意，这套文档不是开发时的代码注释，也不是 API 文档，而是为了让你自己能学明白、后面能讲明白。

这套文档的定位要说清楚：

`它服务的是学习、复盘和面试讲解，不替代设计文档、接口文档和部署文档。`

另外，这套文档最好统一支持三种讲法：

- `30 秒版本`：适合先介绍项目
- `3 分钟版本`：适合完整讲一遍主链路
- `10 分钟深挖版本`：适合应对面试官沿着技术细节继续追问

不管是哪一份解释型文档，默认都要尽量回答六个问题：

- 它在项目里做什么
- 为什么选它
- 替代方案是什么
- 不选它会怎样
- 常见失败点是什么
- 面试常见追问是什么

第一类文档，是 `技术栈角色说明`。
这里要一项一项写清楚：

- React/Next.js 在这个项目里负责什么
- FastAPI 负责什么
- LangGraph 为什么在这里出现
- PostgreSQL 和 pgvector 各自负责什么
- Redis/Celery 为什么要留位置
- Unstructured 负责什么
- LLM 和 Embedding 模型分别承担什么工作

这类文档不能只写定义，必须写到“它在这个项目里的具体职责”。

第二类文档，是 `为什么选它，不选别的`。
比如：

- 为什么前端第一阶段更建议 React + Vite，而不是一上来就 Next.js
- 为什么后端选 FastAPI，而不是 Flask
- 为什么工作流层选 LangGraph，而不是自己硬写流程
- 为什么 RAG 第一阶段先做业务型、窄范围，而不是做成通用知识平台

这类文档的意义不是为了抬高方案，而是为了以后面试时能把“取舍”讲清楚。

第三类文档，是 `技术链路说明`。
这类文档要解释的是：

- 一个 URL 进来之后，内容是怎么被处理的
- RAG 在哪一步介入
- 工作流结果在什么时候固化成稳定快照
- 结果最后怎么导出

这相当于把系统真正跑起来的链路讲清楚。

第四类文档，是 `常见追问准备`。
这部分最好围绕面试高频点去写，比如：

- RAG 在这个项目里具体解决什么问题
- LangGraph 和普通函数调用有什么区别
- 为什么不做多 Agent
- 为什么这版不做 MCP
- URL 解析失败怎么办
- 用户不信任生成结果时，你怎么解释系统的参考依据

这类文档不是面试八股全文背诵，而是把这个项目自己的答案提前整理出来。

第五类文档，是 `失败案例和排错记录`。
这部分很重要，因为真正的项目深挖，很多时候不是问你成功链路，而是问你：

- 做的时候踩过什么坑
- 哪些方案试过但不合适
- 后来为什么改

如果这些东西完全没有记录，后面你很难讲出“真实开发感”。

除此之外，建议再把解释型文档细化成下面几份固定产物，这样后面不容易漏：

- `项目一页纸`
  这份文档专门讲项目解决什么问题、面向谁、输入输出是什么、核心价值是什么。它的作用是保证你第一次介绍项目时不跑偏。

- `系统全链路讲解稿`
  这份文档专门把一次任务从进来到出去完整串起来，说明每一步由哪个模块负责、上下游怎么衔接、结果如何固化成稳定快照并继续导出。

- `技术栈角色卡`
  这份文档一项技术对应一张卡片，解释它在项目里的角色、输入输出、为什么选它、常见风险是什么。

- `核心模块深挖卡`
  这类文档只挑最容易被追问的模块展开，至少要覆盖：
  `Agent 编排`、`RAG`、`工具调用`、`状态/记忆`、`工程兜底`

- `工程化与上线说明`
  这份文档解释缓存、重试、熔断、降级、日志、监控、成本控制分别解决什么问题。

- `评测与效果复盘`
  这份文档解释系统怎么评、评什么、拿什么样本评、优化前后怎么对比。

- `方案取舍与踩坑复盘`
  这份文档记录为什么选当前方案，为什么没选别的方案，真实踩过哪些坑，最后怎么取舍。

- `面试追问题库`
  这份文档围绕项目真实链路整理高频追问，按“问题 -> 回答主线 -> 可展开点”的方式组织。

所以这里正式加一条需求：

`项目在开发过程中，必须同步沉淀学习型、解释型、面试型文档，不能只沉淀代码。`

## 十二、如果后续交给开发 AI，它开工前必须先理解什么

因为你后面很可能会新开对话，把项目继续交给新的开发 AI，所以现在必须把“开发 AI 开工前必读信息”写进需求里。否则每次新开对话，AI 很容易一上来就误解方向。

后续接手开发的 AI，在开始任何实现前，必须先理解下面这些全局信息：

第一，这个项目是一个 `可上线的业务系统`，不是实验脚本，也不是单页演示。

第二，这个项目的主线是：

`内容输入 -> 内容理解 -> RAG 检索参考 -> 工作流生成 -> 稳定快照 -> 结果导出`

不能把主线做偏成聊天产品、通用知识库，或者万能 Agent 平台。

第三，这个项目的第一阶段边界已经定死：

- 要做：内容输入、内容解析、业务型 RAG、工作流结果、稳定快照、导出
- 不做：MCP、多 Agent 平台化、自动发布、重爬虫、GraphRAG、多租户、计费系统

它是业务成立能力，不是装饰能力。后续开发 AI 不能把 RAG 简化成“随便做个向量检索”就结束。

第五，这个项目的结果可见性和证据边界不能被弱化。
如果实现时把风险、不确定项、证据和处理轨迹重新藏回黑盒，那方向就错了。

第六，这个项目不仅要能开发出来，还要能让你学明白、讲清楚。
所以开发 AI 不能只交代码，还要同步输出解释型资料，说明：

- 这个技术为什么加
- 它在项目里做什么
- 为什么不换成别的
- 常见风险在哪里

这部分需求不是附加项，而是项目交付的一部分。

## 十四、这些技术分别是干什么的

### 12.1 React

React 是前端 UI 库，用组件方式搭页面和交互。它适合做后台工作台、表单流、审核页、结果展示页。

### 12.2 Next.js

Next.js 是基于 React 的全栈框架。它除了能写页面，还自带路由、构建、SSR/SSG 和一部分服务端能力。

如果整个项目前后端都想往 Node 体系收，它会更有优势。但你这次后端已经明确要走 FastAPI，所以第一阶段不一定非要上它。

### 12.3 FastAPI

FastAPI 是 Python Web API 框架。它很适合做 AI 工作流后端、文件处理入口、工具调用封装和接口服务层。

### 12.4 PostgreSQL

PostgreSQL 是关系型数据库，适合存用户、任务、审核状态、知识库元数据、日志、导出记录这些结构化数据。

### 12.5 LangGraph

LangGraph 是 Agent 和工作流编排框架。它适合处理这种多步骤、有状态、可暂停、可恢复、可人工介入的 AI 流程。

对你这个项目来说，它和普通“调模型 API”的区别在于：它更适合承接完整业务链路，而不是只做一问一答。

- 项目依赖管理要干净

如果 Python 环境不统一，LangGraph 会很容易把环境问题放大。

### 13.6 PostgreSQL

Windows 下 PostgreSQL 一般通过官方推荐的安装器装。

安装本身不算特别难，但常见坑不少，比如：

- 服务是否自动启动
- 5432 端口是否占用
- 超级用户密码管理
- `psql` 是否进 PATH
- 编码和区域设置

所以它不是第一天就必须装，但如果要尽快贴近最终架构，最好在第一阶段中段补上。

### 13.7 Docker

Docker Desktop 在 Windows 下安装难度中等偏高。

问题不只是装一个程序，而是它依赖：

- WSL 2
- 虚拟化
- Docker Desktop 自己的运行环境

所以 Docker 更适合放在第二批，而不是今天就卡住整个项目。

## 十六、当前机器下的推荐安装顺序

如果按“尽快开工”的目标来排，推荐顺序是这样的：

1. 先把 `Python 3.12` 使用链路理顺
2. 再建立项目虚拟环境
3. 再装 FastAPI 和基础 Python 依赖
4. 前端直接用现有 Node.js + npm 起项目
5. 然后再决定什么时候补 PostgreSQL
6. Docker 放到后面

这个顺序的核心是：

`先保证能开发，再保证贴近最终形态`

## 十七、最小可行开发环境建议

如果目标是尽快做出第一版可演示原型，我建议的最小本地环境是：

- `git`
- `Node.js`
- `npm`
- `Python 3.12`
- `React + Vite`
- `FastAPI`

这里我明确给建议：

### 第一阶段必须装好

- git
- Node.js
- npm
- Python 3.12 可用链路

### 第一阶段建议尽早接入

- FastAPI
- LangGraph

如果你想第一周先把前后端主链路跑通，也可以先不用 LangGraph 把所有流程编排都搭完，但它不应该拖到太后面。

### 可以后装

- pnpm
- Docker
- 本地 PostgreSQL

### 可暂时替代

- PostgreSQL 可以先用 `SQLite` 做本地单机原型，或者直接连云端 Postgres
- Docker 可以先不装，纯本机跑前后端
- Next.js 可以先不选，前端先用 React + Vite 更省心

## 十八、我对技术选型的最终建议

如果目标是又快又稳地做出第一版，我建议第一阶段直接定成下面这套：

- 前端：`React + Vite`
- 后端：`FastAPI`
- 工作流：`LangGraph`
- 数据库：第一阶段开发初期可 `SQLite`，尽快切 `PostgreSQL + pgvector`
- 缓存 / 异步：先留设计位，后续补 `Redis + Celery`
- 内容解析：`Unstructured`
- 模型服务：`DeepSeek 或当前可稳定调用的兼容 API 为主，保留 OpenAI 兼容接入位`
- 部署：`Vercel + Railway + Supabase，定位为低成本演示部署方案`
- 上线目标：`可演示上线，不追求第一阶段正式商用化`

这样选的原因不是保守，而是这套组合最适合你现在的状态：

- 前端基础弱，但 React + Vite 上手成本更低
- 后端明确走 Python
- LangGraph 能保证项目有 Agent/工作流含金量
- 数据层可以先轻一点，再逐步贴近最终架构
- 模型和部署都优先服从你当前的真实环境，而不是先追求理想化的全球生产配置

## 十九、这份方案后面最容易出问题的地方

- 最容易出问题的，不是功能想不全，而是边界重新变松。
- 最容易踩的环境坑，不是 Node，而是默认 Python 继续误走 3.7。
- 最容易写虚的技术点，不是 Agent，而是把 RAG 写成一句“支持知识库检索”。
- 最容易让工期失控的地方，不是前端，而是把 URL 支持范围越写越大，最后滑向重抓取。
- 最容易看起来很高级、实际上拖慢进度的点，是提前搞 MCP、多 Agent 平台化、自动发布和复杂知识治理。
