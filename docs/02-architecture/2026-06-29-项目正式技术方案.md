# 项目正式技术方案

## 一、这份方案现在怎么用

这份文档继续作为本项目的正式技术方案，但从现在开始必须明确区分两层信息：

- `已实现`
  - 当前仓库里已经能运行、能验证、能被操作员实际看到的东西
- `目标 / 待实现`
  - 方向已经定了，但当前还没有完整落地，或者没有被验证到可以诚实宣称完成的部分

后续任何实现、交接、复盘、面试讲解，都不能把这两层混写。

## 二、项目边界仍然不变

Phase 1 仍然只做单任务工作流系统，不扩成平台化底座。

### 2.1 必须围绕的主链路

`内容输入 -> 异步处理 -> 结构化理解 -> 检索参考 -> 工作流结果 -> 人工审核 -> 导出`

### 2.2 明确不扩的方向

- 多 Agent 平台化
- MCP 平台接入
- 重爬虫或全站采集
- 多租户、计费、组织权限
- GraphRAG
- WebSocket-first 实时平台

## 三、当前架构总览

### 3.1 已实现

当前仓库已经落地的是一套前后端分离、后台异步驱动的单体业务系统：

- 前端：`React + Vite`
- 后端 API：`FastAPI`
- 异步任务：`Celery`
- 队列与结果后端：`Redis`
- 数据持久化：`SQLModel + SQLite / PostgreSQL`
- 工作流主链占位服务：`TaskPipelineService`
- 审核门：`ReviewService`
- 导出门：`ExportService`
- 知识索引：本地文件登记 + 异步切块
- 检索：最小词法重叠检索

### 3.2 目标 / 待实现

- 真实模型理解和生成链路
- embedding 向量化与 `pgvector`
- 更完整的知识治理
- 独立审计日志
- 用户认证与权限控制
- 更完整导出格式和下载体验
- 生产级部署加固

## 四、当前仓库的真实能力边界

### 4.1 输入

#### 已实现

- Web UI 可创建：
  - 文本任务
  - URL 任务
  - 文件任务
- 后端接口可创建：
  - 文本任务
  - URL 任务
  - 文件任务
- 任务可携带可选 `knowledge_domain` 检索范围

#### 目标 / 待实现

- 更完整的文件解析链路
- 更细的上传策略、类型治理和预处理

### 4.2 异步主链路

#### 已实现

- 任务创建后立即入队
- worker 在后台推进状态
- 状态机会经过：
  - `queued`
  - `parsing`
  - `understanding`
  - `retrieving`
  - `generating`
  - `review_pending`
  - `reviewing`
  - `approved`
  - `exporting`
  - `completed`
  - `failed`
  - `rejected`
- 前端通过轮询读取任务状态与结果

#### 目标 / 待实现

- 更真实的阶段级失败恢复
- 更细的重试与幂等策略验证
- 更深的异步运行观测

### 4.3 结构化理解

#### 已实现

- 后端会产出稳定结构的理解结果
- 当前字段主要包括：
  - `summary`
  - `audience`
  - `key_points`
  - `risk_points`
  - `uncertain_items`
  - `input_quality`

#### 目标 / 待实现

- 真实模型驱动的理解结果
- 更完整的风险点、不确定项、素材片段输出

这里必须诚实说明：当前结构化理解的“接口形状”已经继续往前走了一步，已经开始显式暴露输入质量、风险点和不确定项，方便审核人判断当前主链到底稳不稳；但“业务智能深度”仍然没有成立，它现在更像是可审查的工程骨架，不是成熟模型能力。

### 4.4 检索与知识索引

#### 已实现

- 本地知识文件可通过 `POST /knowledge/index-local` 注册
- worker 会异步读取本地文件、按段切块、写入可检索记录
- 检索服务已经是真实实现，不是纯 stub
- 当前检索方式是：
  - 基于词法 token 重叠排序
  - 支持按任务 `knowledge_domain` 过滤
  - 返回可展示来源、标题、片段、命中理由
- 文件任务当前会读取真实上传文本参与检索
- URL 任务当前会抓取公开 HTML，优先抽取 `article / main` 正文，并保留 `title / extractor / quality_flags` 供 reviewer 判断抽取质量后再参与检索
- 工作流结果现在会显式保留：
  - `evidence_used`
  - `uncertainties`
  - `manual_checks`
  - `context_summary`
  - `processing_trace`

#### 目标 / 待实现

- embedding 向量化
- `pgvector` 检索
- 重排
- 更细的 metadata 设计
- 更稳定的知识域运营流程
- URL 任务更稳的文章级正文抽取、清洗和失败恢复

更准确的说法是：

- `已实现最小可用的本地知识索引 + 词法检索 + 基础范围收口`
- `已实现最小可审查的上下文与证据可见性`
- `已实现最小可审查的 URL 抽取质量暴露，但还不是成熟文章抽取链`
- `尚未实现目标态 embedding RAG`

### 4.5 审核门

#### 已实现

- 任务进入 `review_pending` 后，必须显式开始审核
- 审核中可编辑：
  - 理解摘要
  - 受众
  - 关键点
  - 检索命中项
  - 工作流草稿
  - reviewer note
  - not adopted items
- 可执行：
  - 保存审核
  - 批准
  - 驳回
  - 驳回后重跑

#### 目标 / 待实现

- 更细的差异展示
- 更完整的审核台视图
- 审核动作独立审计记录

### 4.6 导出门

#### 已实现

- 导出必须基于 `approved_snapshot`
- 审核通过前不能导出
- 已有最小 `markdown` / `structured_text` 导出任务
- 后端能返回导出任务状态和文件路径
- 后端已提供导出制品下载路由
- 前端已接通导出任务轮询与下载动作

#### 目标 / 待实现

- 更多导出格式
- 导出历史与权限约束
- 更完整的导出管理体验

这里必须写死一条规则：

`导出权威来源是 approved_snapshot，不是审核前原始生成结果，也不是前端临时拼接状态。`

## 五、模块边界

- 创建任务

- 展示理解结果、检索来源、工作流结果

### 5.2 后端 API

- 审核动作
- 导出任务创建与查询

#### 目标 / 待实现

- 更细的重试与补偿策略

## 七、当前安全与运行事实

### 7.1 已实现

- URL 做 SSRF 基础校验
- 拦截回环和常见内网地址
- URL 抓取后会对最终响应落点再次做 SSRF 校验，避免重定向把请求带到本地或内网
- 文件上传限制扩展名和大小
- 已支持基于环境变量的最小 Bearer 访问门禁
- compose 默认把 PostgreSQL / Redis / MinIO 只绑定回环地址
- 检索内容在语义上被当作参考资料展示，而不是系统指令

### 7.2 目标 / 待实现

- 更完整的用户认证与权限控制
- 独立审计链路
- 更完整的密钥治理
- 更完整的生产部署验证
- 线上 HTTPS / 反向代理 / 备份策略实测闭环

当前更准确的说法是：

- `已做最小输入与本地暴露面控制`
- `未完成生产级安全与运维验证`

## 七点五、当前主链已经开始正面处理的问题

当前主链不是只为了“把结果跑出来”，而是已经开始显式暴露前五类核心问题，方便继续往真实 AI 应用收口：

- 输入质量问题
  - 当前已经开始记录输入来源类型、抽取长度和质量标记
- 召回问题
  - 当前仍是最小词法检索，但已经保留检索范围收口与 reviewer-visible 证据边界
- 上下文组织问题
  - 当前已经开始输出 `context_summary`，明确这轮生成到底装配了哪些上下文板块
- 幻觉与证据使用问题
  - 当前已经开始输出 `evidence_used`、`uncertainties`、`manual_checks`
- 工作流状态一致性问题
  - 当前已经有审核门、批准后快照、导出权威来源，以及 reviewer 可见 `processing_trace`

这仍然不等于“问题已经解决”，但它意味着这条单主链已经不再把这些问题藏在黑盒里，而是开始让系统自己暴露它们。

## 十、结论

当前项目可以被准确描述为：

- 已经具备真实异步骨架
- 已经具备真实审核门
- 已经具备审核后导出权威快照
- 已经具备最小本地知识索引和词法检索
- 已经具备文本、URL 的 Web 创建入口
- 已经具备可选最小 Bearer 访问门禁
- 但仍然没有完整用户认证、独立审计日志、完整验收评测和生产加固

后续所有技术说明，都必须基于这个口径继续推进。
