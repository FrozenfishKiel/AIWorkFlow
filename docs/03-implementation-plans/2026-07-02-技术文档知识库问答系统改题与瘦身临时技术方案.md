# 技术文档知识库问答系统改题与瘦身临时技术方案

## 这份文档的定位

这不是最终正式技术方案。

这份文档的作用只有一个：

- 把当前仓库从 `AI内容生产与运营工作流系统` 改题为 `技术文档知识库问答系统` 时，应该删什么、留什么、怎么改、最终做成什么样，一次性说清楚。

后续如果这条路线确认无误，再把这里的结论正式吸收进大技术方案。

## 一、这次改题的核心判断

当前仓库之所以要改，不是因为“还差一点点没做完”，而是因为题目本身已经偏了。

偏掉的地方主要有两个：

1. `URL` 被做成了主链重点之一，但这条线天然容易滑向抓取、反爬、动态渲染、正文抽取、失败恢复，工期和复杂度都明显超出当前阶段应该承受的范围。
2. `内容生产与运营工作流` 这个题目把“内容理解、RAG、工作流、导出、审计、前台结果页”绑得太紧，导致项目越来越像一个复合业务系统，而不是一个边界清晰、可被稳定讲清楚的 AI 应用开发项目。

因此，这次不是“在原题目上继续补”，而是：

- `彻底改题`
- `主动瘦身`
- `只保留 AI 应用开发主链`

## 二、改题后的新项目定义

新项目名称暂定为：

`技术文档知识库问答系统`

新项目的目标是：

- 接收技术文档
- 对文档进行切块与索引
- 让用户围绕知识库提问
- 系统完成检索增强回答
- 回答附带可见引用来源

一句话描述：

`一个面向固定技术文档资料的 Agent 化 RAG 问答系统。`

这里要特别说明两点：

1. `题目是知识库问答`
   - 对外讲项目时，主产品身份是技术文档知识库问答系统
2. `技术内核保留 Agent 化主链`
   - 对内实现时，不是只有“检索一下然后拼答案”，而是要保留问题理解、检索、证据约束、回答生成、引用展示这条可讲成 Agent 化链路的技术骨架

## 三、这次改题的硬约束

这几条不是建议，是本次修改的硬约束。

### 3.1 必删，不允许“保留但降级”

下面这些内容，后续要按删除处理，不做“先藏起来以后再说”。

- `URL 输入能力`
- `URL 抽取与正文解析链`
- `内容生产 / 洗稿 / 改写 / 成稿建议` 这套业务壳
- `任务工作台` 叙事
- `前台任务列表`
- `前台导出历史`
- `前台当前任务状态面板`
- `内容运营 / 品牌资料 / 文案生产` 方向的文档口径

### 3.2 能删就删，不为了“复用率”留下垃圾碎片

如果某个模块的存在只会：

- 误导后续实现方向
- 在代码里留下旧题目语义
- 让测试继续背旧包袱

那么应当删除，而不是保留。

### 3.3 测试策略必须重写

后续不再采用“模块测试通过 + 局部页面能看”就算完成的策略。

新的验证标准必须以 `完整项目用户流` 为中心：

1. 后端能否从零启动
2. 前端能否从零启动
3. 用户能否进入页面
4. 用户能否导入知识资料
5. 用户能否输入问题
6. 点击后是否立即有反馈
7. 是否真的返回回答
8. 是否真的带引用来源

也就是说，后续自测必须按“你自己扮演真实用户，从头到尾完整跑一遍”的方式做，而不是只从开发者视角做局部验证。

## 四、新项目主链

改题之后，项目主链改为：

`技术文档接入 -> 文档清洗/切块 -> 知识索引 -> 用户提问 -> 检索召回 -> 证据筛选 -> 回答生成 -> 引用展示`

这条主链要满足两个要求：

1. `对外是经典知识库问答`
   - 用户视角足够直接
   - 页面足够干净
2. `对内能讲成 Agent 化链路`
   - 可以解释问题理解、查询改写、检索策略、证据约束、回答生成这些步骤各自做了什么

## 五、前端最终形态

前端收口为：

- `一个经典问答页`

页面主内容只保留：

- 知识库名称 / 简介
- 一个问题输入框
- 一个提交按钮
- 一个回答展示区
- 一个引用来源区

前端默认不再展示：

- 任务列表
- 当前任务详情
- 导出历史
- 审计时间线
- 工作流阶段面板
- 内容成稿 / 风险与待确认 / 可复用素材

如果后续确实还需要知识文档管理入口，应该采用下面这种处理方式：

- 单独的知识库管理页
- 或问答页中的次级管理入口

但它不应该喧宾夺主，更不能重新长成“工作台首页”。

## 六、后端最终形态

后端主 API 应围绕两条线：

### 6.1 知识库线

- 文档上传 / 登记
- 文档切块
- 向量或检索画像生成
- 文档列表 / 文档详情

### 6.2 问答线

- 用户提问
- 检索召回
- 证据筛选
- 生成回答
- 返回引用来源

这里要特别注意：

- 问答主链不再围绕 `Task -> WorkflowResult -> Export` 设计
- 新主链不再以“任务完成后导出结果”为中心
- 新主链的权威输出应该是：
  - `answer`
  - `citations`
  - `retrieval_context`

## 七、Agent 化技术内核怎么保留

这次不做多 Agent 工作流，不做 Agent 平台，不做角色市场。

但仍然要保留 `Agent 化内核`，具体体现在下面这条单主链里：

1. `Question Understanding`
   - 识别用户问题意图
   - 必要时做查询改写
2. `Retrieval`
   - 基于知识库做检索召回
3. `Evidence Selection`
   - 对候选片段做裁剪与筛选
4. `Answer Generation`
   - 基于证据回答问题
5. `Citation Packaging`
   - 将引用片段和来源一起返回

所以后续项目可以被准确描述为：

`一个采用单 Agent 编排链的技术文档知识库问答系统`

这样做的原因是：

- 保留 Agent 味道
- 保留可讲述的技术链路
- 不引入真多 Agent 的额外复杂度
- 避免项目重新变胖

## 八、哪些东西保留，哪些东西删除

## 8.1 应保留的底座

这些模块与新方向直接相关，应该作为复用底座保留：

- `FastAPI` API 骨架
- `SQLModel` 数据模型基础
- 知识文档模型与 repository
- 切块逻辑
- `RetrievalService`
- `RetrievalProfileProvider`
- `EmbeddingService`
- `DeepSeek` provider 封装
- 中文前端基础工程
- 基础验证脚本

## 8.2 应重写的模块

这些模块可以借壳，但语义必须重写：

- 问答主链服务
- 前端问答页
- task / result 相关 schema
- 当前任务结果视图
- 前端 copy 文案
- 技术方案与 README 描述

## 8.3 应删除的模块

下面这些内容不应继续留在正式主链里：

- URL ingestion service
- URL 相关输入校验入口
- URL 输入表单选项
- 与 URL 抽取质量相关的前台展示
- 内容生产工作流结果字段
- 内容成稿视图
- 前台任务列表主区
- 前台任务状态快照
- 前台导出中心

## 九、对当前“坑点”的正式处理

之前识别出来的坑，这次按下面方式处理。

### 9.1 旧 schema 残留

处理原则：

- 不接受“旧字段先留着用”
- 新主链若不再需要，就改或删

目标：

- API 命名、前端类型、文档术语全部转向知识库问答语义

### 9.2 前端残留任务心智

处理原则：

- 不再保留前台任务心智
- 问答页就是问答页

目标：

- 用户打开页面只会理解为“技术文档问答”，不会理解成“异步任务工作台”

### 9.3 异步主链过重

处理原则：

- 重新判断异步是否仍是主链刚需
- 若不是刚需，就从正式主链删除

当前建议：

- `问答链` 优先改成同步请求响应
- `知识库索引` 是否异步，单独评估

如果同步足够支撑当前项目目标，就不要为了“工程完整感”强留 Worker 作为主链依赖。

### 9.4 导出链残留

处理原则：

- 导出不是新题目的主价值
- 如果保留只会拖累主链，就删除

当前建议：

- 从正式主链删除导出
- 不再把导出作为核心交付面

### 9.5 Agent 味道不够

处理原则：

- 不靠前台轨迹面板堆 Agent 味
- 靠后端单 Agent 编排链建立技术含金量

目标：

- 对外是经典问答产品
- 对内能讲清楚 Agent 化决策链

## 十、后续实施顺序

后续改造建议按下面顺序推进：

1. `先改文档与边界`
   - 把新项目定义写清楚
   - 把删除清单写清楚
2. `先删前台旧壳`
   - 先把 URL、任务列表、内容生产视图从前端移除
3. `再改后端主链`
   - 把主链从“任务工作流”收口为“问答链”
4. `再清理旧 schema 与旧服务`
   - 把残留的内容生产与 URL 模块删掉
5. `最后按完整项目做用户流测试`
   - 不是只测接口
   - 不是只测单页
   - 是从启动到提问到回答完整走一遍

## 十一、新的完成标准

这次改题完成，不按“还能跑旧东西”来判断，而按下面这些条件判断：

- 页面打开后是经典技术文档问答页，而不是任务工作台
- 前台不再暴露 URL、任务列表、导出历史、任务状态
- 用户能导入技术文档资料
- 用户能就知识库提问
- 系统能返回回答
- 回答能附引用来源
- 启动与完整用户流已按真实使用方式自测通过
- 旧题目相关的主链代码、页面和文档已删除，不残留伪入口和误导性口径

## 十二、这份方案的结论

这次改题不是“轻微转向”，而是一轮有意识的瘦身重构。

但它仍然不属于推倒重写，因为当前仓库里真正有价值的 AI 应用底座仍然存在：

- 文档接入
- 切块索引
- 检索
- 模型调用
- 前后端工程骨架

真正应该删掉的，是旧题目的业务壳、展示壳和错误主线。

所以这次修改的核心原则可以收成一句话：

`删掉不属于技术文档知识库问答系统主链的东西，只保留 AI 应用开发真正需要的那条链。`
