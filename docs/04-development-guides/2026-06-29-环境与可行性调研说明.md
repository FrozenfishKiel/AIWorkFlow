# 环境与可行性调研说明

## 一、这份文档现在回答什么

这份文档只回答三件事：

1. 当前这台机器，是否已经具备进入项目第一阶段开发的最低条件。
2. 哪些准备工作已经实际完成，哪些还只是方案落位。
3. 后续如果继续做系统级安装，应该怎么做、装到哪里、有哪些风险需要先确认。

这里的“第一阶段”仍然是我们已经定下来的目标：做一个可演示上线的内容任务工作台，而不是一次性做成正式商业化平台。

## 四、当前机器仍然存在的客观问题

### 4.1 系统默认 Python 仍然混乱

虽然项目专用环境已经可用，但系统默认 Python 仍然是有问题的：

- `python --version` 返回 `Python 3.7.0`
- `pip --version` 绑定的是 `D:\Anaconda3\lib\site-packages\pip (python 3.7)`
- `py -0p` 仍然登记了一个 `Python 3.12` 路径：
  - `C:\Users\frozenfish\AppData\Local\Programs\Python\Python312\python.exe`
- 但 `py -3.12 --version` 无法启动，报错为无法创建进程

这说明系统层仍然保留着失真的 Python 3.12 启动器记录。后续如果有人直接使用：

- `python`
- `pip`
- `py -3.12`

就可能重新踩回错误链路。

因此当前必须坚持下面这个规则：

- 只使用 `D:\Anaconda3\envs\ai-content-ops\python.exe`
- 只使用这个环境里的 `pip`
- 不把默认 `python` 当成项目入口

### 4.2 Docker 已安装并可运行

当前机器已经可以正常使用 Docker：

- `docker --version` 可用
- `docker compose version` 可用
- `docker info` 可用
- `infra/docker-compose.yml` 已经实际拉起基础服务

这轮还补到了一个更关键的事实。我们已经实际拉起过 Docker Desktop 安装器，并尝试把安装目标改到 `D:`。根据安装日志与最终安装结果：

- 安装包下载体积约为 `628.9 MB`
- 安装器解包时仍会使用 `C:\Users\frozenfish\AppData\Local\Temp\DockerDesktopInstallers`
- 安装阶段要求可用空间约 `3432 MiB`
- 在 `C:` 清理前，安装器判定系统盘可用空间仅约 `709 MiB`，因此直接拒绝安装
- 清理后安装成功，程序目录实际落在 `D:\Docker\Docker`
- Docker 数据目录实际落在 `D:\ai-content-ops\docker-hyperv-data`

这说明 Docker 的关键经验不是“装不上”，而是“即使目标目录放在 `D:`，官方安装器仍会先检查 `C:` 的可用空间”。

## 六、需求可行性复核

从需求和当前准备情况一起看，项目仍然是可做的，而且具备推进价值。

### 6.1 为什么可做

因为我们已经把几个最容易失控的点压住了：

- 第一阶段只做一个明确知识域的 RAG
- URL 只支持公开网页或可控站点
- 首目标是可演示上线，不是正式商用平台
- 人工审核链路不延后
- 基础服务已经纳入准备范围，但不会反客为主阻断主链路

这决定了项目不是“做一个大而全的平台”，而是在做一个边界清晰、能够试用和讲解的业务型 AI 原型。

### 6.2 现在最大的现实风险

目前最大的风险不是代码写不出来，而是下面这些工程问题：

1. 系统默认 Python 仍然容易误用。
2. Docker 已安装，但 Docker Desktop 在 Windows 上的安装路径与数据路径仍需继续保持收敛，避免后续新增内容重新回流到 `C:`
3. PostgreSQL 在 Windows 上不能直接回退到宿主绑定目录，否则会再次触发权限位错误
4. `Celery` 现在只有包，没有最终运行形态。
5. 文档已经不该继续把“计划中”和“已完成”混写。
