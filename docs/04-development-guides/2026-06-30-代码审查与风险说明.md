## 二、本轮已经修掉的真实风险

### 1. 驳回重跑先入队再校验

这个问题已经修掉了。现在 `rerun` 路由会先校验状态，再允许 Celery 入队，避免非法状态偷偷进入后台任务。

### 2. 审核后导出读错数据源

当前导出只读 `approved_snapshot`，不再从审核前草稿或者前端临时拼接结果导出。

### 3. 审核草稿被轮询静默覆盖

前端现在已经显式保护这个问题，只有在强制同步场景才会回写本地草稿。

### 6. 导出制品直接暴露服务器路径

这个问题本轮已经收口。现在下载走 API 路由，并且会校验导出状态、文件存在性、以及路径是否仍然落在受控导出目录下。

## 三、当前仍然存在的主要风险

### 1. 还没有真实生产级 RAG

当前检索虽然已经从“只按词重合个数排”推进到“多信号词法排序 + 上下文限量装配”，但仍然没有 embedding、pgvector 和正式重排链，不能把现在的引用命中质量当成最终效果。

### 2. URL 任务还没有成熟的文章级抽取

这轮已经把 URL 任务从“占位文本”推进到“公开 HTML 基础正文抽取 + 可见的抽取器/标题/浅抽取标记”，也补上了重定向最终落点的 SSRF 再校验；但仍然没有成熟的文章级正文抽取、噪音清洗和失败恢复，后续还要继续补。

### 3. 还没有完整认证与权限系统

当前已经有最小 Bearer 访问门禁，但还没有登录、用户身份、权限分层。这依然是正式上线前必须继续补的硬缺口。

### 4. 还没有独立审计实体

虽然 `review` 和 `approved_snapshot` 已经保留了关键信息，但独立 `AuditLog` 还没落地，后续责任追踪能力有限。

### 5. 生产部署收口还不能说完成

当前 prod override 不能诚实地说已经把外露端口都收住了，这部分需要后续再验证和修正。

## 四、当前测试覆盖怎么理解

已经覆盖：

- API 单元与集成测试
- API evaluation / retrieval regression 测试
- root acceptance 测试
- Web 单元测试
- compose / build / import / compile 校验

还没覆盖完整：

- 浏览器级 e2e smoke
- 压力测试
- 更系统的风险测试
- 正式部署环境下的真实冷启动回归

## 五、建议的 review 顺序

1. 先看 `review / approved_snapshot / export` 这条边界
2. 再看 `input_security / upload` 这条安全边界
3. 再看 `retrieval_service / task_pipeline_service / evaluation` 这条检索范围边界
4. 再看前端 `reviewDraft / normalizeTaskRecord` 这条状态同步边界
5. 最后再看 `core/security / api.ts` 这条最小访问门禁边界

## 六、review 时不要误判的点

- 现在有真实异步主链，但不代表已经是完整生产项目
- 现在有真实 knowledge 索引与检索，但不代表已经是完整 RAG
- 现在有导出闭环，但不代表导出产品体验已经做完
- 现在有最小 Bearer 门禁，但不代表已经具备完整认证体系

review 的核心不是“它看起来像不像一个大系统”，而是“当前说自己已经做到的东西，是否真的做到并被验证了”。
