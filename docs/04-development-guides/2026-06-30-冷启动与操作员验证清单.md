# 冷启动与操作员验证清单

这份清单是给后来接手的人用的。目的不是解释“项目理想上应该怎样”，而是告诉接手的人，当前这套仓库怎么一步一步冷启动，怎么确认它真的能用。

## 一、先把基础服务拉起来

在仓库根目录执行：

```powershell
docker compose -f infra/docker-compose.yml up -d
```

然后看容器是否都起来了：

```powershell
docker compose -f infra/docker-compose.yml ps
```

当前应该至少看到：

- `api`
- `worker`
- `postgres`
- `redis`
- `minio`

## 二、安装依赖

### API

```powershell
cd apps/api
D:\Anaconda3\envs\ai-content-ops\python.exe -m pip install -r requirements-dev.txt
```

### Web

```powershell
cd apps/web
npm install
```

## 三、先跑统一校验

回到仓库根目录：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/qa/verify.ps1 -Scope all
```

这一步现在会校验：

- compose config
- compose prod override config
- API compile/import
- API pytest
- root acceptance pytest
- Web build
- Web test

如果这一步不过，不要继续往下做人工验收，先修失败项。

## 四、启动本地开发进程

如果要手动联调，而不是只看测试结果，可以分别启动：

### API

```powershell
cd apps/api
D:\Anaconda3\envs\ai-content-ops\python.exe -m uvicorn app.main:app --reload
```

### Worker

```powershell
cd apps/api
D:\Anaconda3\envs\ai-content-ops\python.exe -m celery -A app.tasks.celery_app:celery_app worker --loglevel=info
```

### Web

```powershell
cd apps/web
npm run dev
```

## 五、人工验收顺序

### 1. 健康检查

访问：

- `http://127.0.0.1:8000/health`

预期：

- 返回 `{"status":"ok"}`

如果后端配置了 `API_ACCESS_TOKEN`，后续除 `/health` 以外的接口请求都必须带：

```text
Authorization: Bearer <your-token>
```

如果你走前端联调，则把同一个值写进前端环境变量 `VITE_API_ACCESS_TOKEN`。

### 2. 创建文本任务

在前端工作台创建一个文本任务。

预期：

- 任务进入 `queued`
- 随后按顺序推进到 `parsing / understanding / retrieving / generating / completed`

### 3. 创建文件任务

在前端工作台切换到 `file`，上传一个允许的 `.txt` / `.md` 文件。

预期：

- 任务创建成功
- 任务记录的 `input_type` 是 `file`
- 同名文件不会直接覆盖历史上传物

### 4. 创建 URL 任务

在前端创建一个公网 URL 任务。

预期：

- 可以创建成功
- 本地地址、内网地址、`localhost` 之类应被拦截
- 如果公网 URL 最终重定向到本地或内网落点，任务应在后台失败，而不是继续抽取
- 任务详情视图里应能看到 URL 输入的抽取质量信号，例如 `quality_flags`、`metadata.title`、`metadata.extractor`

### 5. 结果回看与稳定快照

打开一个已完成任务，检查：

- 理解结果
- 引用命中
- 工作流结果
- `risk_points / uncertain_items / input_quality`
- `evidence_used / manual_checks / context_summary / processing_trace`
- `approved_snapshot`

预期：

- 任务已经进入 `completed`
- 页面能看到稳定快照和导出入口
- 回看区当前应能看到：
  - `risk_points`
  - `uncertain_items`
  - `input_quality`
  - `evidence_used`
  - `manual_checks`
  - `context_summary`
  - `processing_trace`

这一步的意义，不只是看“有没有草稿”，而是看系统有没有把问题显式暴露出来：

- 如果 `input_quality` 已经很差，后面答不好先别急着怪生成层
- 如果 `evidence_used` 很弱，优先回看检索层
- 如果 `context_summary` 和实际任务不匹配，优先回看上下文组织
- 如果 `uncertain_items` 明明很多，但草稿却写得特别肯定，要重点盯生成约束

### 6. 导出链

对已完成任务发起 markdown 导出。

预期：

- 生成 `ExportJob`
- 前端会继续轮询导出任务状态
- 导出成功后 `ExportJob` 进入 `completed`
- 前端可点击下载导出制品
- 导出内容来自稳定快照 `approved_snapshot`，不是页面临时拼接结果

## 六、当前已知的人工验收边界

- 当前检索是最小词法检索，不要按生产 RAG 效果预期来验
- 当前已经开始显式暴露输入质量、风险、不确定项、证据和处理轨迹，但这不等于这些问题已经被完整解决
- 当前导出体验已经支持最小下载闭环，但还没有完整导出历史与管理页
- 当前有最小 Bearer 门禁，但这不等于完整认证与权限系统
