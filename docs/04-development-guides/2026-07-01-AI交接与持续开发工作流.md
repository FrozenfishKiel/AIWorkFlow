# AI 交接与持续开发工作流

这份文档不是项目需求，也不是技术方案补充。它只解决一件事：当下一个 AI 接手这个仓库时，应该按什么工作纪律继续开发，什么事情可以自己做，什么事情必须停下来，怎么保证不偏方向、不把项目做散、也不把责任边界做没了。

## 第一章 先记住，这不是随便写着玩的 demo

这个项目的定位，是面向 `AI 应用开发岗位` 的作品仓库，不是“能跑就行”的实验仓。后续任何实现、修改、测试、review，都要围绕下面这几个目标收口：

- 项目要能讲清楚主链是什么
- 项目要能讲清楚边界是什么
- 项目要能讲清楚哪些已经实现，哪些还没有实现
- 项目要能讲清楚 AI 应用里的核心风险是怎么被暴露、收敛和审查的

所以后续开发时，不能为了快就偷偷扩范围，也不能为了好看就把未完成能力包装成“已经具备”。

## 第二章 接手后先按什么顺序看

不要一上来就改代码。先按下面顺序读：

1. `README.md`
2. `AGENTS.md`
3. `docs/01-project-specs/` 里的最新需求文档
4. `docs/02-architecture/2026-06-29-项目正式技术方案.md`
5. `docs/04-development-guides/`

重点不是“看过就算”，而是先建立三个判断：

- 当前项目主链到底是什么
- 当前项目明确不做什么
- 当前仓库里哪些东西是真的已经落地并被验证过的

如果这三件事没建立起来，就不要急着开工。

## 第三章 当前项目主链，只能沿这条线继续推进

当前 Phase 1 主链必须继续围绕这一条：

`内容输入 -> 异步处理 -> 结构化理解 -> 检索参考 -> 工作流结果 -> 人工审核 -> 导出`

这条线的意思不是“先写个草稿再说”，而是每一层都要问自己：

- 输入质量有没有暴露出来
- 检索证据有没有暴露出来
- 上下文组织有没有暴露出来
- 生成结果有没有把不确定性带出来
- 审核有没有形成硬门
- 导出是不是只认审核后快照

后续如果新增功能，必须能挂回这条主链。挂不回去的东西，不要乱加。

## 第四章 明确不扩的方向，不要自作聪明

当前明确不扩：

- 多 Agent 平台化产品
- LangGraph 业务编排平台化
- MCP 平台接入
- GraphRAG
- 多租户、计费、组织权限
- 大规模爬虫或全站采集
- 为了“看起来高级”而临时加的大而全基础设施

如果某个想法明显会把项目从“单任务 AI 工作流”带偏成“平台底座”，就停下来，不要绕路。

## 第五章 开发工作方式：自主推进，但不是失控推进

这个项目要求 AI 自主开发，但“自主”不是指随便往下写，而是要按工期、按步骤、按检查点往前推。

接手后默认遵循下面原则：

- 不要反复等用户说“继续”
- 只要没有真实阻塞，就自己按计划推进
- 每完成一段，就立刻做对应验证
- 如果发现方向分歧，先停下来收口，不要偷偷换题
- 如果发现问题能自己解决，就直接解决
- 如果确实存在高风险外部阻塞，再汇报

这里真正要避免的是两种失控：

- 一种是完全不推进，什么都等人指挥
- 另一种是看起来很勤奋，但一直在绕路，最后把项目做歪

## 第六章 分步完成，不要一次把所有问题混成一锅

后续开发默认按下面的节奏推进：

1. 先选当前最值钱、最阻塞主链可信度的问题
2. 先补测试，再补实现，再补文档
3. 跑局部验证
4. 跑范围验证
5. 更新技术方案和操作文档
6. 再进入下一段

不要出现下面这种情况：

- 代码改了，但没测试
- 测试过了，但文档还是旧的
- 文档写了，但代码和文档描述不一致
- 主链某一层已经改了，但 reviewer 视图看不到变化

也就是说，每一段开发都要形成一个可交付的小闭环。

## 第七章 Harness 式纪律，必须长期保持

这里的 harness 纪律，不是口号，而是后续每一轮都要执行的工作规矩。

### 1. 能自己继续，就不要停

默认持续推进，除非遇到这些情况：

- 网络、VPN、依赖源、系统环境真的阻塞了
- 涉及删除系统关键内容或高风险环境操作
- 需求方向出现真实分歧
- 需要用户提供真实样本做人工终审

除此之外，不要把“需要继续吗”当成阶段性输出。

### 2. 每一轮都要有可验证结果

任何“完成了”的说法，都要先有验证证据。至少要回答：

- 改了什么
- 用什么命令验的
- 实际结果是什么
- 还剩什么风险

如果没有验证，不要说完成。

### 3. 不要把问题藏进黑盒

AI 应用开发最怕的不是能力弱，而是能力弱但装作没问题。

所以后续实现要优先让系统暴露：

- 输入质量
- 检索质量
- 上下文构成
- 不确定性
- 证据使用
- 审核痕迹

这比“先把结果生成出来”更重要。

## 第八章 当前仓库已经形成的一些好习惯，后面不要丢

这部分是这段开发里已经沉淀出来的项目习惯。它们不一定都写在系统规则里，但对保持项目质量很重要。

### 1. 代码、测试、文档要同步收口

后续每次改动，如果改变了行为，就默认同步改：

- 后端测试
- 前端测试
- 技术方案
- 冷启动或审查文档

不要让 README 和技术方案变成“好看的旧故事”。

### 2. 让 reviewer 真能看懂，而不是只给模型看

这个项目后面一定会有人审，所以字段设计、前端展示、终审文档，都要站在 reviewer 视角收口。

要优先保证 reviewer 看得到：

- 输入是怎么来的
- 质量怎么样
- 检索用了什么
- 为什么命中
- 生成时用了哪些证据
- 哪些地方仍然不确定

### 3. 运行垃圾要及时清

仓库里不允许到处散落缓存和零碎产物。后续继续保持：

- 运行产物尽量进 `.runtime/`
- `__pycache__`、`.pytest_cache` 这类缓存跑完清掉
- 需要忽略的内容及时进 `.gitignore`

### 4. 不要误报能力边界

现在项目虽然已经有：

- 真异步主链
- 真审核门
- 真审核后导出快照
- 真本地知识索引
- 真可运行检索

但仍然没有：

- 真实 embedding RAG
- pgvector 实际召回链
- 多 Agent 平台
- 完整认证权限
- 完整审计系统

后续描述项目时，必须继续守住这条诚实边界。

## 第九章 多 agent 怎么用，才算用对

这个项目允许分配多个 agent，但不是为了制造热闹。

正确用法是：

- 当任务可以并行，而且写入范围不冲突时再分
- 能复用已有 agent，就不要一味新增
- agent 主要用于探索、review、或局部实现
- 主控制者必须负责最后集成、验证和文档同步

错误用法是：

- 一个问题反复开新 agent
- agent 之间做重复劳动
- 明明主线没收口，还不停分叉

如果 agent 位受限，就优先复用已有 agent，不要让“agent 开不出来”变成停工理由。

## 第十章 什么情况下必须停下来，不要硬顶

后续开发如果遇到下面这些情况，应该停下来收口，而不是继续堆代码：

- 发现当前实现开始偏离主链
- 发现一个问题的修法会改变项目边界
- 发现为了补一个点，开始引入一整套新平台
- 发现代码虽然能跑，但已经没法诚实解释给面试官
- 发现测试结果和文档口径对不上

这里“停下来”不是让你不做事，而是先回到技术方案和主链边界重新对齐，再继续。

## 第十一章 后续每轮结束时，默认要做什么

每一轮开发结束后，默认做下面几件事：

1. 检查注释
2. 检查实现有没有偏离需求和技术方案
3. 自己先做一轮代码 review
4. 跑必要测试
5. 补测试文档或操作说明
6. 更新风险说明

这里的“注释检查”不是要把代码写成教材，而是至少保证：

- 核心属性有说明
- 核心流程有说明
- 容易误解的边界有说明

尤其是 AI 主链、审核边界、安全边界，这些地方的注释不能省。

## 第十二章 给下一个 AI 的实际开工建议

下一个 AI 接手时，推荐按这个顺序开始：

1. 重新读一遍 `README.md`、`AGENTS.md`、技术方案和开发指南
2. 跑一次 `scripts/qa/verify.ps1 -Scope all`
3. 查看当前未完成风险，先选一个最值钱的问题
4. 先写测试，再补实现
5. 改完以后跑局部测试和统一校验
6. 更新文档
7. 再进入下一段

不要从“我能再加什么功能”开始，而要从“当前主链最不成熟的那一层是什么”开始。

## 第十三章 最后一句话

这个仓库接下来的开发，不需要一个只会生成代码的 AI，需要的是一个能负责的工程协作者。

所谓负责，落到这里其实就是几件事：

- 不偏方向
- 不藏问题
- 不乱扩范围
- 不伪报完成
- 每一轮都留下可验证、可交接、可审查的结果

后续谁接手，谁就按这个标准继续往下做。
