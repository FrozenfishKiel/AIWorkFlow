# 人工终审包说明

这份文档不是技术方案，也不是代码审查说明。它只解决一件事：当项目推进到需要你做人审时，你应该看什么、按什么顺序看、看到什么算正常、看到什么必须拦下来。

## 一、什么时候需要你介入

默认情况下，你不需要盯日常实现，也不需要反复发“继续”。

你只在下面三种时候介入：

- 需要提供真实业务样本
  - 例如真实 URL、真实文本、真实上传文件
- 我遇到外部硬阻塞
  - 例如依赖源、网络、系统环境、第三方库兼容性
- 正式人工终审
  - 也就是这份文档对应的场景

## 二、人工终审时看什么

人工终审不要只看“草稿像不像能发”。当前项目至少要按下面顺序看：

1. 输入质量
2. 检索命中
3. 上下文摘要
4. 生成结果
5. 审核修改
6. 导出结果

对应到系统当前字段，就是：

- `understanding.input_quality`
- `understanding.risk_points`
- `understanding.uncertain_items`
- `retrieval_hits`
- `workflow_result.evidence_used`
- `workflow_result.context_summary`
- `workflow_result.manual_checks`
- `workflow_result.processing_trace`
- `review`
- `approved_snapshot`

## 三、看这些字段时怎么判断

### 1. 输入质量

先看：

- `source_kind`
- `quality_flags`
- `extracted_length`
- URL 场景再补看：`input_quality.metadata.title`
- URL 场景再补看：`input_quality.metadata.extractor`

如果这里已经显示输入很短、URL 抽取很浅、或明显有质量问题，后面答不好不能只怪生成层。

### 2. 检索命中

先看：

- 命中了哪些来源
- reason 是否讲得通
- 有没有明显该命中但没命中的材料

如果 evidence 明显不对，优先回看检索链，不要先改草稿。

### 3. 上下文摘要

先看：

- `selected_hit_count`
- `context_sections`
- 是否有重复命中被去掉

如果上下文里关键板块缺了，或者明显塞了太多噪声，优先回看上下文组织，而不是先调 prompt。

### 4. 生成结果

重点看：

- 草稿结论是否过度肯定
- `evidence_used` 和草稿内容是否真的对应
- `uncertainties` 是否被如实保留
- `manual_checks` 是否合理

如果 `uncertainties` 很多，但草稿口气却非常确定，这就是需要拦下来的点。

### 5. 审核修改

重点看：

- reviewer 有没有把高风险内容压下来
- `not_adopted_items` 是否解释了放弃哪些内容
- 修改后是否还保留了证据链

### 6. 导出结果

最终只确认一件事：

- 导出内容是不是来自 `approved_snapshot`

不是的话，直接算边界事故。

## 四、什么情况必须拦下

下面这些情况，人工终审应直接判定“不能过”：

- 输入质量已经明显异常，但系统还装作很确定
- 检索证据和草稿内容对不上
- 高风险 claim 没有证据还写成定论
- `approved_snapshot` 和导出结果不一致
- reviewer 修改后，风险字段被静默吃掉

## 五、终审时你会拿到什么

后续正式终审时，我会尽量把材料收口成一包可直接看的内容，而不是口头汇报：

- 样本输入
- 检索结果
- 上下文摘要
- 生成草稿
- 审核修改结果
- 导出结果
- 测试通过/失败说明

如果某一轮有未完成项，我也会把未完成项单独列出来，不和已完成部分混写。
