# 剩余任务收口与首验判断

这份文档沿用旧文件路径，但当前内容已经更新为最新状态。它的目的只有两个：

1. 把当前已经确认收缩后的结构性剩余任务说死，避免后续再把它说成一团模糊的“大方向”。
2. 基于当前仓库、验收入口和人工终审文档，判断“只剩这最后一项结构任务时，项目距离第一次验收测试还有什么差距”。

## 一、先把“结构性剩余项”说死

当前 Phase 1 范围内，剩余的结构性任务只保留一项：

1. `下一阶段能力升级包`

这里的“结构性”，指的是它们都不是单点修补，而会同时牵动：

- 数据模型
- 后端服务边界
- API
- 前端 reviewer 可见视图
- 测试
- 文档与验收口径

## 二、已完成补记：独立 AuditLog 审计链

这一项现在已经不是剩余任务，但需要在这里留痕，避免后面又被误判成“还没做”。

### 2.1 已经落地了什么

当前仓库已经新增并接通：

- `AuditLog` 独立实体
- 动作类型与成功/失败枚举
- `TaskPipelineService` 写入：
  - `pipeline_completed`
  - `snapshot_persisted`
- `ExportService` 写入：
  - 导出创建
  - 导出开始
  - 导出完成
  - 导出失败
- `GET /tasks/{task_id}/audit-logs`
- task 详情页中的动作时间线
- 后端与前端对应测试

### 2.2 这一项现在还没覆盖什么

当前已完成的是“最小独立审计链”，还没有扩展到：

- 带操作者身份的审计记录
- 通用审计中心
- 跨租户审计隔离
- 安全合规级日志平台
- 更丰富的重跑 / 运维动作留痕

这部分不再单独算 Phase 1 的结构性剩余项，而是并入后续升级包。

## 三、任务一：下一阶段能力升级包

### 3.1 这个任务为什么现在是唯一剩余项

虽然它内部很大，但当前仍把它视为一个结构性包，而不是拆成多个独立遗留项，原因是它们共同指向同一件事：

`把当前“工程骨架成立，但 AI 能力仍是最小占位”的系统，推进到第一次真正可验收的业务能力形态。`

也就是说，这一包不是简单的“继续加功能”，而是把下面几条能力一起从占位态推进到真实态：

- 模型理解与生成
- 向量化 RAG
- 认证与权限
- 生产级安全与运维加固

### 3.2 建议拆分的子任务

#### B1. 真实模型调用链

当前 `TaskPipelineService` 的结构化理解和工作流结果，更多是 reviewer-friendly 的稳定工程骨架。

这一段要补的是：

- 模型调用封装层
- 结构化输出协议
- understanding / workflow_result 的真实模型驱动版本
- 模型失败时的降级或错误暴露策略

这里的目标不是“一上来做复杂多模型路由”，而是：

- 先有一条真实、可替换、可观测的模型链
- 保持当前 reviewer-visible 字段别倒退

#### B2. 向量化 RAG 与 `pgvector`

当前检索是最小词法检索，已经有基础范围收口与可见证据边界，但还不是目标态 RAG。

这一段要补的是：

- embedding 入库链
- `pgvector` 检索链
- metadata 设计
- 检索与重排策略
- 与当前 `knowledge_domain`、可见摘录、命中理由的兼容

目标不是做知识平台，而是：

`把当前最小检索升级成真实业务型 RAG。`

#### B3. 认证与权限

当前只有最小 Bearer 门禁，这不能支撑第一次更正式的对外验收。

这一段要补的是：

- 登录入口
- 基础用户身份
- 最小权限边界
- reviewer / operator 的访问约束

注意这里的目标仍然不是多租户平台，而是：

- 把“匿名本地工具”推进到“最小可控业务系统”

#### B4. 生产级安全、压测与运维加固

这一段不是锦上添花，而是让系统能从“能演示”变成“能正式跑第一次业务验收”的兜底层。

至少应覆盖：

- 安全边界复查
- 关键失败路径验证
- 压测 / 并发一致性最小验证
- 运行与部署说明收口
- 验收期的监控 / tracing / 问题定位手段

### 3.3 完成标准

这个能力包完成后，项目不应再只是：

- 有异步链路
- 有 reviewer-visible 字段
- 有最小检索

而应进入下面这个状态：

- 理解和生成来自真实模型
- 检索来自真实向量链
- reviewer 看到的证据和不确定性仍然可追
- 系统有最小身份边界
- 验收时出现失败，能知道卡在哪里，而不是只知道“它挂了”

## 四、浅调研：只剩这一个结构任务时，能不能进行第一次验收测试

先把“第一次验收测试”分成两种，不然很容易说乱。

### 4.1 如果指的是“仓库工程验收”

也就是：

- 跑统一校验
- 跑 root acceptance
- 看当前最小主链是否未回退

那答案其实是：

`现在就已经可以做，而且仓库已经在做。`

依据：

- `tests/README.md` 已经把 root acceptance 的当前目标写清楚
- `tests/acceptance/test_task_review_export_acceptance.py` 已经覆盖最小闭环
- `scripts/qa/verify.ps1 -Scope all` 已经把这条入口纳入统一校验

所以如果“第一次验收”只是工程意义上的仓库验收，那不需要等最后这一个结构任务做完。

### 4.2 如果指的是“第一次正式人工 / 业务验收”

也就是更接近下面这类场景：

- 用真实 URL / 文本 / 文件样本跑任务
- 人工检查输入质量、证据命中、上下文摘要、审核修改、导出结果
- 判断这是不是一条能开始给真实内容团队试用的链路

那答案是：

`当前项目已经能进入仓库级工程验收；等最后这一项能力包完成后，会非常接近首验条件，但仍然不应自动视为“可以直接验收”，还需要补齐验收前置条件。`

### 4.3 首验前还缺什么

这些不是第三个结构性大任务，但它们是正式首验前置条件。

#### C1. 真实样本包

当前文档已经多次写明：

- 正式人工终审需要真实业务样本
- 第一阶段内部验收建议用 `30 到 50` 个真实任务样本

但当前仓库里：

- `tests/samples/` 还是空的，只有 `.gitkeep`

这意味着：

- 验收规则有了
- 验收入口有了
- 但真正的验收材料还没进仓或还没由你提供

所以如果没有真实样本，正式首验不能开始。

#### C2. 首验样本分层与通过标准

当前 spec 已经给了高层指标方向：

- 任务跑通率
- RAG 命中有效率
- 审核通过率
- 导出成功率

但还缺一份真正用于首验执行的“样本分层 + 通过阈值”清单，例如：

- URL 样本多少条
- 文本样本多少条
- 文件样本多少条
- 哪些任务允许“可人工继续编辑”算通过
- 哪些情况必须直接判失败

没有这份清单，正式首验会变成主观讨论，不是可复用流程。

#### C3. 一次真实人工终审包

当前已经有：

- [人工终审包说明](./2026-07-01-人工终审包说明.md)

但这还是“说明文档”，不是一包具体可验收材料。

正式首验时，仍然需要有人把下面这些内容按样本打包出来：

- 样本输入
- 检索结果
- 上下文摘要
- 生成草稿
- 审核修改结果
- 导出结果
- 测试通过/失败说明

也就是说：

- 规则已经有了
- 材料模板已经有了
- 但首轮真实验收包本身还没有实例化

## 五、结论

### 5.1 结构性结论

当前剩余工程已经可以收口成一项：

1. `下一阶段能力升级包`

### 5.2 验收结论

如果说的是仓库级工程验收：

- `现在就能做`
- 而且已经有现成入口

如果说的是第一次正式人工 / 业务验收：

- `不是只做完最后这一项工程就自动开始`
- 还需要补三类验收前置条件：
  1. 真实样本包
  2. 样本分层与通过标准
  3. 一次真实人工终审材料包

### 5.3 更直白的一句话

`最后这一项结构任务解决的是“项目本身还缺什么”；首验前置条件解决的是“拿什么、按什么标准去验它”。`

前者做完，不代表后者自动存在。

## 六、第二个大点的最新口径调整清单

这一节不是新方案全文，只记录当前已经确认的方向调整，后续第二个大点默认按这份口径继续推进。

### 6.1 已确认的方向调整

#### D1. 不走多 Agent 方向

第二个大点后续仍然是：

- 单任务
- 单工作流
- 固定步骤链

不是多个智能体角色协作，也不做 agent 间分工叙事。

#### D2. 模型只作为能力层，不作为流程控制层

模型职责收窄为：

- 理解
- 生成

检索能力职责单独存在：

- 向量化
- 召回证据

下面这些仍由普通工程层负责：

- 状态机
- 审计
- 导出
- 权限
- 失败记录

#### D3. 内容提取先走确定性链路，再交给模型

当前方向明确为：

- 先抓正文 / 提文本
- 再做输入质量标记
- 再交给模型做理解与生成

不是把原始网页源码或原始复杂文档直接整体扔给模型。

#### D4. 取消“人工审核硬门”作为主链中心

这是这轮最大的产品口径调整。

后续不再把人工放在：

- 逐条审批
- 导出前卡口
- 后台持续盯盘

新的口径是：

- 主链自动跑完
- 结果自动进入导出 / 落盘链路
- 人主要看后台记录与事后问题，而不是同步审批

#### D5. `review` 不再表示业务审批流

后续讨论里的 `review`，默认指：

- 工程 review
- 代码问题检查
- 漏洞和风险排查

不再把它等同于产品流程里的人工审批步骤。

#### D6. 后台记录必须足够强

因为不再依赖人工前置审核，所以后台至少必须能回看：

- 输入内容
- 提取质量
- 检索证据
- 生成结果
- 导出结果
- 关键动作
- 失败记录
- 重跑记录

### 6.2 第二个大点需要据此重构的现有模块

这部分不是逐步实施计划，而是后续一定会被波及的改造面清单。

#### R1. 主链状态定义

当前主链里与人工审核强绑定的状态，需要重新评估：

- 这四个旧状态已经从当前主链状态集合移除，只保留在历史讨论和兼容语义里

需要决定：

- 哪些状态直接删除
- 哪些改造成自动链路中的内部状态
- 哪些保留为后台诊断信息

#### R2. `ReviewService`（已退场）

这一层已经从主链退场，当前更准确的收口方式是保留兼容记录语义，不再恢复为审核门核心服务。

在新口径下，需要判断：

- 是否整体移除
- 是否改造成后台检查 / 反馈记录服务
- 是否只保留一小部分“人工修正任务”的运维能力

但它不应继续作为主链中心。

#### R3. review 相关 API

当前相关接口包括：

- `start`
- `save`
- `approve`
- `reject`
- `rerun`

后续要重新定义：

- 哪些接口删除
- 哪些接口改成运维 / 诊断入口
- 哪些只保留重跑能力

#### R4. `approved_snapshot`

这一层原本服务于“审核后快照”。

新口径下需要重新命名或重新定义它的职责边界，避免继续暗示“必须人工批准后才有权威结果”。

可以保留“最终导出快照”这种工程边界，但不应再依赖人工审批语义。

#### R5. 前端审核区

当前前端有明显的审核编辑区和审核动作按钮。

这块后续不应继续作为主页面核心操作区，而需要改造成更适合新口径的东西，例如：

- 后台记录查看
- 任务细节诊断
- 失败原因查看
- 证据链与生成结果回看

#### R6. 导出链

当前导出依赖“审核通过后才能继续”这条旧边界。

后续要改成：

- 自动主链完成后可直接导出或自动落盘
- 导出结果仍然必须可追踪
- 导出内容仍然必须绑定最终稳定快照，而不是任意中间态

### 6.3 第二个大点的新主链口径

后续默认按下面这条线理解第二个大点的能力升级，不再回到旧的人工审核表述：

`输入 -> 提取 -> 输入质量标记 -> 理解 -> 检索 -> 上下文装配 -> 生成 -> 自动导出/落盘 -> 后台可追踪记录`

如果后面需要人工参与，它也应优先被定义为：

- 后台回看
- 诊断
- 运维处理

而不是前置审批。

## 七、当前进展补记（2026-07-01 后端首切已完成）

这里补一条已经落地的事实，避免后面继续拿旧口径判断当前状态：

- 后端主链已经完成第一刀重构：
  - `TaskPipelineService` 成功结束后直接进入 `completed`
  - 结果会自动固化到 `approved_snapshot` 这个遗留字段名下
  - 导出已经不再依赖人工审核批准，只依赖稳定快照存在
- 这意味着“人工审核硬门”已经不再是后端主链成立条件。
- 但这不等于第二大项已经整体完成，因为下面这些仍然是结构性残余：
- legacy `ReviewService` 和 `/reviews/*` 已经退场
- 前端 `TaskDetailView / TaskConsolePage` 已经完成去中心化，不再把审核区当成页面中心
  - `approved_snapshot` 仍然是遗留命名，还没有完成语义收口或替换

所以当前最准确的判断是：

- 后端主语义已经往“自动链路 + 事后回看”推进了一步
- 第二大项里与 legacy review 相关的结构残留已经收口，当前只剩 `approved_snapshot` 遗留命名与后续审计增强边界需要并入后面唯一剩余的大项统一处理
