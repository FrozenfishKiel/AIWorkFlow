# 第二大项后端首切实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or equivalent task-by-task execution discipline. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把当前主链从“人工审核后才能导出”改成“流水线产物自动固化为稳定快照，并可直接进入导出链”，同时把改动控制在后端主语义与验证面内。

**Architecture:** 这一切片不直接拆掉全部 review 代码，而是先把后端权威边界改掉。具体做法是：保留现有持久化字段与大部分接口形状，先让流水线完成时自动生成稳定快照并进入可导出状态，再让导出服务消费这个自动快照而不是等待人工批准。等这个新语义稳定后，再做 review 路由与前端审核区的去中心化改造。

**Tech Stack:** `FastAPI`, `SQLModel`, `pytest`, `Celery task boundary stubs`, `React/Vite`（本切片仅做残余检查，不主动改前端大面）

## 方案选择

### 采用方案：保留旧字段名，先改权威语义

- 保留 `approved_snapshot` 字段，避免这一步引入 schema 迁移。
- 把它的实际职责临时改成“自动固化的最终导出快照”。
- 让 `TaskPipelineService` 在生成结束时直接写入这个快照。
- 让任务在流水线完成后直接进入 `completed`，从而复用现有前端的“可导出”判断和导出失败回滚逻辑。

### 暂不采用方案 A：先删 review 路由和 review 状态

- 这样改动面太大，会把后端主语义、前端页面、适配层和 acceptance 一起拉进第一刀。
- 风险不是实现不了，而是很难在一轮里证明没有新残余。

### 暂不采用方案 B：新增 `final_snapshot` / `ready` 新字段新状态

- 这会引入数据库结构变化和更广泛的类型变更。
- 当前最优先目标是把主链从人工审核依赖中解开，不是追求一次性命名完美。
