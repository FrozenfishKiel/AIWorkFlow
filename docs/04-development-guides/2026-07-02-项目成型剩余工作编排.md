# 项目成型剩余工作编排

这份文档不是验收清单，而是当前“把项目做成型”的开发编排稿。

这里的“成型”指的是：

- 不再只是工程骨架
- 不是只有异步主链和可视化回看
- 而是已经具备真实模型理解、真实业务型 RAG、可继续迭代的业务域内容，以及最小可运营的运行闭环

## 一、当前确认的两条主开发主线

### 主线 A：真实模型理解与生成链

当前状态：

- `已完成首轮落地`

目标：

- 把当前 `TaskPipelineService` 里的占位理解与占位工作流结果，替换成真实模型输出
- 保持当前 reviewer-visible 字段边界不倒退
- 保持后端、前端、导出、审计、测试链路继续成立

这条线要完成的内容：

- 模型提供商封装层
- DeepSeek 适配器
- 结构化输出协议
- understanding prompt 与 workflow prompt
- understanding 真实模型输出
- workflow_result 真实模型输出
- 模型失败、空结果、脏结果、超时处理
- 最小 tracing / 调试字段

当前已落地结果：

- 已新增统一 generation provider 层
- 已接通 DeepSeek 结构化 understanding / workflow 生成
- 已保留 deterministic fallback，避免测试和无 key 环境失效
- 已补 `.env.local` 读取
- 已补模型脏结构归一化兜底
- 已通过真实 DeepSeek 烟雾验证与仓库 `api` 校验

### 主线 B：真实业务型 RAG

当前状态：

- `已完成首轮落地`

目标：

- 把当前最小词法检索升级成真实业务型 RAG
- 保持当前 `knowledge_domain`、证据可见性、命中理由、前端回看边界继续成立

这条线要完成的内容：

- embedding 入库链
- 向量存储落位
- `pgvector` 检索链
- chunk / metadata 设计收口
- 召回排序与必要的轻重排
- 命中结果继续返回 reviewer-visible 片段和理由
- 回归样例补齐

当前已落地结果：

- 已新增 retrieval profile provider 层
- 已接通索引阶段 `retrieval_text` 生成
- 已接通 embedding 向量落盘
- PostgreSQL 下已兼容 `pgvector` 向量列，SQLite 测试环境下回退 JSON
- 已接通查询阶段混合排序：向量相似度 + 词法可解释信号
- 已保留 `knowledge_domain`、source visibility、reason 字段契约
- 已补索引、检索、回归、任务主链相关测试

## 二、让项目真正“能用”还要接上的两层

这两层不是替代上面两条主线，而是两条主线打通后必须接上的落地层。

### 落地层 C：业务域内容落地

目标：

- 先选 1 个业务域，把真实任务和真实知识资产放进系统
- 不追求一开始就多业务域并行

要做的内容：

- 占位业务域定义
- 占位知识材料集合
- 占位任务样本集合
- 结果判读模板

### 落地层 D：最小可运营闭环

当前状态：

- `已完成首轮收口`

目标：

- 让系统不只会跑，还要能定位问题、最小受控运行、对外解释清楚

当前已落地内容：

- 最小登录 / 用户身份边界
  - legacy 静态 Bearer 门禁
  - 单操作者密码登录 + 短期 token
- 关键失败路径收口
  - 启动时校验认证配置完整性
- 运行说明收口
- 配置说明收口
- FastAPI lifespan 启动收口

下一轮仍可继续增强的内容：

- 基础监控 / tracing 接入位
- 更完整的生产级安全、压测与运维加固
- 更细粒度权限与多用户治理

## 三、推荐执行顺序

### Phase 1：模型链先落地

先做：

- DeepSeek 适配器
- 模型封装层
- understanding 结构化输出
- workflow_result 结构化输出

原因：

- 不先把模型链接通，后面的 RAG 很难进入真实联调
- 当前最大的“车壳感”来自这里

### Phase 2：RAG 升级落地

再做：

- embedding 入库
- `pgvector` 检索
- metadata
- 召回 / 结果兼容

原因：

- 模型链接通后，才能看清真正的检索质量问题
- 这一步会引入数据库 / 向量层变更，应该放在模型链后集中处理

### Phase 3：业务域占位内容与端到端联调

再做：

- 先用占位业务域资料跑通
- 看任务输入、检索、理解、生成、导出是否联起来

原因：

- 用户已经明确允许先用占位知识资料与占位业务域
- 这能让开发不再等待真实资料才能推进

### Phase 4：最小可运营闭环补齐

最后做：

- 配置/部署/运行说明
- tracing 与问题定位入口
- 更完整的生产级安全与运维收口

原因：

- 这部分不先于真实模型链和真实 RAG
- 但项目成型前必须补上

## 四、具体分工建议

### 工作流 1：模型链

负责人：主线程 / 核心实现

适合并行分拆的子任务：

- 模型配置与 provider 封装
- understanding / workflow prompt 设计
- 结构化 schema 与解析
- API key / 运行配置接线

### 工作流 2：RAG

负责人：独立子线程 / 并行实现

适合并行分拆的子任务：

- embedding schema 设计
- repository / service 改造
- 检索排序与返回契约兼容
- 回归测试与质量样例

### 工作流 3：业务域占位资料

负责人：轻量并行子线程

适合并行分拆的子任务：

- 编一个占位业务域
- 编第一批占位知识资料
- 编占位任务样本

### 工作流 4：最小可运营闭环

负责人：持续收尾 / 与主线程并行补齐

适合并行分拆的子任务：

- 运行文档
- tracing 入口
- 错误收口
- 生产级安全 / 运维加固
- 细粒度权限演进

## 五、时间估算

以下是“开发时间”估算，不含你后续人工测试时间。

### 最乐观

- 真实模型链：1 到 2 天
- 真实 RAG：2 到 3 天
- 占位业务域与联调：0.5 到 1 天
- 最小可运营闭环：1 到 2 天

总计：`4.5 到 8 天`

### 更稳妥

- 真实模型链：2 到 3 天
- 真实 RAG：3 到 5 天
- 占位业务域与联调：1 天
- 最小可运营闭环：1 到 2 天

总计：`7 到 11 天`

## 六、Harness 能不能自主开发完成

结论：

- `大部分可以`
- `但不是完全不需要你`

### Harness 可以自主完成的部分

- DeepSeek 接入与封装
- prompt / schema / 结构化输出
- 当前 placeholder 理解与生成替换
- 当前词法检索升级为 embedding / vector 检索
- 占位业务域与占位知识资料
- 端到端代码联调
- 测试与文档同步

### Harness 需要你最终确认或提供的部分

- 真实业务知识资料
- 真实任务样本
- 你更偏好的输出风格
- 任何数据库 / schema 迁移的明确放行

## 九、当前最合理的开发判断

如果按“项目成型”推进，而不是按“先去验收”推进，那么当前最正确的开发口径是：

1. 先打通真实模型链
2. 再打通真实业务型 RAG
3. 再补占位业务域联调
4. 再收尾生产级加固与权限演进

也就是说：

- 现在不该再把主注意力放在验收包上
- 而应该把“工程骨架”推进成“真实 AI 应用”
