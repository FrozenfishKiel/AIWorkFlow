# 首验人工测试执行单

这份文档只服务当前这一次事：

- 你像真实用户一样，手动把这款产品从头到尾用一遍

它不是自动化测试说明，也不是开发文档。它是给你实际点页面、传资料、看结果、判断问题用的。

## 一、这轮人工测试到底在测什么

这轮不是测“代码有没有语法问题”，也不是测“单元测试过没过”。

这轮重点测的是：

- 这个产品作为一个真实可用的工作台，链路顺不顺
- 真实知识资料进来后，检索像不像样
- 三种输入方式能不能正常使用
- 输出结果是不是已经到了“可以继续往下加工”的程度
- 导出、下载、审计回看这些收尾环节是不是也能闭环

一句话说：

- 这轮测的是“像用户一样用，这个产品到底能不能用了”

## 二、从 0 开始先把系统打开

如果你现在是在本地仓库里自己做人工测试，那就按下面顺序来。

这一步不是“用户操作流程”的一部分，但你必须先把系统跑起来，否则后面没法像用户一样点页面。

### 1. 最简单的启动方式

现在优先用一条命令启动，不要自己一条条敲。

在仓库根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/dev/start-local-stack.ps1
```

这条命令会自动处理：

- 已缓存的基础容器
- 本地 API
- 本地 worker
- 本地前端
- 前端端口冲突时自动换端口

脚本最后会告诉你应该打开哪个地址。

### 2. 打开脚本打印出来的页面地址

脚本会打印一个类似这样的地址：

```text
http://127.0.0.1:5175
```

你直接复制到浏览器打开就行。

注意：

- 不一定每次都是 `5175`
- 如果 `5173` 被别的项目占了，脚本会自动往后找空闲端口
- 所以一定以脚本打印出来的地址为准

### 3. 如果一条命令启动失败，再手动分步看

只有在上面那条命令失败时，你再回头看分步启动。

先起基础服务：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/dev/start-local-infra.ps1
```

然后再分别起 API、worker、web。

### 4. 停止本地测试环境

如果你后面想停掉自己起的本地 API / worker / web，可以运行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/dev/stop-local-stack.ps1
```

### 7. 如果打不开，先这样判断

你可以按这个顺序看：

1. 浏览器页面是否能打开脚本打印出来的地址
2. API 健康检查能否打开 `http://localhost:8000/health`
3. API 终端有没有报错
4. worker 终端有没有报错
5. 前端终端有没有报错

只要页面能打开，而且任务提交后能继续往后跑，人工测试就可以正式开始。

## 五、从页面开始，一条条点

下面开始才是真正“像用户一样使用”的测试流程。

建议你严格按顺序来，不要乱跳。

### 第 1 步：先确认页面本身是活的

你先看这几个地方：

- 页面是不是正常打开了
- 有没有整页报错
- 左边有没有 `New task`
- 左边有没有 `Knowledge index`
- 有没有 `Task list`
- 右边有没有详情面板

判定标准：

- 看到完整工作台布局，算通过
- 白屏、整页报错、一直转圈不出界面，算失败

### 第 2 步：如果出现登录页，先测登录

如果你打开页面后看到的是登录面板，而不是工作台，就这样做：

1. 找到 `Operator login`
2. 在 `Username` 填用户名
3. 在 `Password` 填密码
4. 点 `Sign in`

你要看：

- 能不能进入工作台
- 顶部会不会出现 `Signed in as ...`

判定标准：

- 登录后进入工作台，算通过
- 登录后报错、回不到工作台、进入后接口还是 401，算失败

如果你打开页面后没有登录页，直接进入工作台，那这一项就跳过。

### 第 3 步：先导入知识资料

在 `Knowledge index` 区按这个顺序填：

1. `Title`
2. `Source path`
3. `Source type`
4. `Domain`
5. 点 `Register local knowledge`

每导入一份后，你要继续点：

1. 在下面文档列表里选中刚刚那条
2. 看右侧的 `Document detail`
3. 必要时点 `Refresh`
4. 看 `Chunk preview`

你要看什么：

- 文档有没有进列表
- 状态会不会从排队变成已索引
- `Chunks` 数字是不是大于 0
- `Chunk preview` 里有没有真正的正文内容

判定标准：

- 能登记、能索引、能看到合理切块，算通过
- 只看到文件路径、没有正文、切块为空、状态卡住，算失败

### 第 4 步：测文本任务

在 `New task` 区这样点：

1. `Input type` 选 `Text`
2. `Knowledge domain` 填你要测的业务域
3. `Content` 粘贴任务文本
4. 点 `Create task`

点完以后，你看：

1. `Task list` 里有没有新任务
2. 状态会不会往后变
3. 右边详情区会不会出现结果

详情区重点看这些块：

- `Understanding`
- `Retrieval hits`
- `Workflow result`
- `Traceability`
- `Audit timeline`

判定标准：

- 有理解结果、有检索结果、有工作流结果、有审计记录，算通过
- 只有任务创建成功但后面没结果，算失败

### 第 5 步：测文件任务

还是在 `New task` 区，这次这样点：

1. `Input type` 选 `File`
2. `Knowledge domain` 填业务域
3. `File` 里选择文件
4. 点 `Create task`

你要看：

- 文件任务能不能创建成功
- 任务详情里的摘要是不是在说文件正文
- 检索命中是不是和文件正文相关

判定标准：

- 结果明显是基于文件内容生成的，算通过
- 看起来只吃到了文件名，或者内容明显不对，算失败

### 第 6 步：测 URL 任务

还是在 `New task` 区：

1. `Input type` 选 `URL`
2. `Knowledge domain` 先按需要填
3. `Content` 填 URL
4. 点 `Create task`

你要看：

- URL 任务能不能跑完
- `Understanding` 里摘要像不像正文
- `Input metadata` 里有没有 `title`、`extractor`
- `Quality flags` 有没有明显提示

判定标准：

- 能抽到正文、结果基本围绕正文，算通过
- 抽到导航、杂项、明显不是正文，算失败

### 第 7 步：测导出

找到一个已经 `Completed` 的任务，然后在详情区 `Export` 里这样点：

1. 点 `Export markdown`
2. 等状态变化
3. 如果出现下载按钮，点 `Download artifact`
4. 再点一次 `Export structured text`

同时去看下面的 `Export history`：

- 有没有新导出任务
- 状态会不会变化
- 能不能下载

判定标准：

- 能创建导出、能完成、能下载、导出历史有记录，算通过
- 导出卡住、下载失败、内容不对，算失败

### 第 8 步：测审计回看

在任务详情区找到 `Audit timeline`，往下看每一条记录。

你至少应该看到这类动作：

- `Pipeline completed`
- `Snapshot persisted`
- `Export created`
- `Export started`
- `Export completed`

判定标准：

- 时间线完整、顺序合理、每条不是空壳，算通过
- 缺关键动作、顺序很乱、信息太空，算失败

## 六、推荐测试顺序总结

如果你嫌上面字多，就按这个最短顺序测：

1. 打开页面
2. 如有登录先登录
3. 先导 1 到 3 份知识资料
4. 测 1 条文本任务
5. 测 1 条文件任务
6. 测 1 条 URL 任务
7. 对完成任务做 2 次导出
8. 回看审计时间线

## 七、这一轮人工测试最该盯的判断点

你不是只看“有没有结果”，而是重点判断下面这些。

### 1. 检索是不是像真的

你要问自己：

- 它命中的资料是不是你本来就会拿来参考的
- 明明该命中的资料有没有没命中
- 命中理由是不是说得过去

### 2. 输出是不是能继续用

你要问自己：

- 这结果是不是已经能给下游继续改，而不是要全部重写
- 它给出的拆解、提示、待确认项是不是有实际帮助

### 3. 风险暴露是否够

你要问自己：

- 它有没有老老实实把不确定项说出来
- 有没有把待确认内容说死
- 有没有把风险点藏起来

### 4. 三种输入谁最不稳

你要问自己：

- 文本、文件、URL 哪一种最容易跑偏
- 是抽取问题、检索问题，还是生成问题

## 八、你测完后最好怎么记录

建议你每条问题都按这个格式记。

```text
任务类型：text / file / url
任务名称：
问题位置：知识索引 / 理解 / 检索 / 工作流结果 / 导出 / 审计
问题描述：
是否稳定复现：是 / 否
你认为的严重程度：高 / 中 / 低
截图或样本位置：
```

## 九、你测的时候如果出现这些情况，优先记下来

这些是最值钱的问题：

- 明明该命中的知识资料没有命中
- 输出把待确认项写成确定事实
- URL 抽出来明显不是正文
- 文件任务看起来没有真正吃到正文
- 导出结果和详情页稳定快照不一致
- AuditLog 看不出到底发生了什么
- 某一类任务稳定比另外两类差很多

## 十、这轮测试后怎么理解结果

如果你最后发现的是下面这些问题，不要混为一谈。

### 1. 主链问题

例如：

- 创建不了任务
- 跑不完
- 导出失败
- 审计缺失

这类属于系统链路问题，优先级最高。

### 2. 检索问题

例如：

- 命中的资料不对
- 该中的没中
- 同义表达找不到正确资料

这类属于召回和排序问题。

### 3. 结果质量问题

例如：

- 摘要不准
- 输出太空
- 风险点不够
- 待确认项暴露不充分

这类属于理解和生成质量问题。

### 4. 材料问题

例如：

- 你给的知识资料本身太少
- 业务域混乱
- 任务描述不清

这类不一定是系统本身有 bug。

## 十一、这轮测完后你最应该回答我的问题

你测完后，最有价值的是告诉我这几件事：

1. 哪一类输入最不稳
2. 哪一类问题最多
3. 哪些结果你觉得已经“能用”
4. 哪些结果虽然跑通了，但你完全不能接受
5. 哪些问题是你认为必须在下一轮先修的

只要你能回答这五个问题，下一轮优化优先级就会非常清楚。
