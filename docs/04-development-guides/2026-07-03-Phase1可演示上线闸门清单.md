# Phase 1 可演示上线闸门清单

这份清单不是“建议做什么”，而是“做完这些才允许上线什么”。

先把口径锁死：

- 本清单完成后，允许上线的范围是 `Phase 1 可演示上线`。
- 这里的“上线”，指外部可访问、可让真实用户或甲方完整体验一次正式主链。
- 这里的“上线”，不等于“正式商用上线”。
- `file://` 打开的本地网页、`localhost`、`127.0.0.1`、开发机临时服务，都不算上线。
- 任一阻塞项未通过，都不允许上线。

项目正式口径以当前需求和技术方案为准：

- 第一阶段上线目标是 `可演示上线，不是正式商用上线`。
- 正式主链是 `商品信息输入 -> 任务理解 -> 业务资料匹配/利用 -> 卖点提炼 -> 多类型内容生成 -> 风险与口径检查 -> 结果交付`。
- 正式 API 主入口是 `/product-content/jobs`，不是旧的 `/tasks` 任务台心智。

---

## 一、上线定义

完成本清单后，可以对外宣称的是：

`这是一套可访问、可登录、可真实生成、可导出结果的电商商品内容生产系统 Phase 1 演示版。`

这里的“可访问”必须满足：

- 不是本地 HTML 文件直接打开。
- 不是只在开发机浏览器里访问 `localhost`。
- 至少要有一套真实部署后的 Web 访问地址，且能连到真实部署后的 API。

不能对外宣称的是：

- 已正式商用
- 已完成生产级安全收口
- 已具备多租户、计费、组织权限
- 已具备成熟运维体系
- 已验证 Docker 生产编排可以直接作为正式生产方案

---

## 二、产品与界面闸门

### 阻塞项 1：正式对外界面只能保留两层

- [ ] 官网首屏是正式入口，不再暴露旧工作页、旧原型页、旧任务台入口。
- [ ] 工作台主页是正式操作页，不再暴露旧的任务列表式工作台心智。
- [ ] 站内所有主按钮都能点通；不能点通的入口要么删除，要么改成纯展示且无误导。

通过标准：

- 首页只承担产品说明和进入工作台。
- 工作台只承担登录、输入、生成、查看结果、导出。
- 不存在“点了没反应”的正式入口。

### 阻塞项 2：界面不能出现与当前项目不符的内容

- [ ] 不展示图片生成结果、成品效果图、需要调用生图模型的假交付内容。
- [ ] 不展示套餐、价格、品牌背书、头部品牌信赖之类的假商业包装。
- [ ] 不展示任务列表、导出记录、资料底座管理、复杂流程监控这类用户看不懂也不想看的半成品模块。
- [ ] 不展示未接入功能的“解决方案 / 应用场景 / 使用方式”类假导航；如果没有真实页面，就不要保留。

通过标准：

- 用户第一眼能明白这是“电商商品内容生产”产品。
- 用户不会被假功能、假页面、假商业文案误导。

### 阻塞项 3：工作台展示的结果必须符合当前业务边界

- [ ] 结果区只展示当前真实支持的文案类产物。
- [ ] 至少保留当前项目约定的文案结果视图，不额外塞入图片、套餐、可信度包装、结果交付壳子。
- [ ] 如保留风险提示、参考依据，必须来自真实主链结果，而不是前端写死的装饰数据。

通过标准：

- 页面上看到什么，后端就真能产出什么。
- 页面上看不到的能力，不拿来对外说已经支持。

---

## 三、正式主链闸门

### 阻塞项 4：必须只认正式主链，不再拿测试链冒充主链

- [ ] 正式生成入口走 `/product-content/jobs`。
- [ ] 正式查询入口走 `/product-content/jobs/{task_id}`。
- [ ] 正式导出入口走 `/exports` 和 `/exports/{export_job_id}/artifact`。
- [ ] 前端正式页面不依赖旧 `/tasks`、`/knowledge` 页面心智完成用户主流程。

通过标准：

- 用户从首页进入工作台后，不需要理解旧任务系统，也不需要进入旧页面。
- 浏览器里完整走一遍：登录 -> 提交商品信息 -> 等待生成 -> 查看结果 -> 导出下载。

### 阻塞项 5：主链必须真的跑完

- [ ] 提交一次真实商品信息后，任务状态能完整推进到完成态。
- [ ] 生成结果不是前端假数据，也不是静态模板回显。
- [ ] 导出基于稳定快照生成，不是从前端临时拼页面。
- [ ] 导出文件能实际下载并打开。

通过标准：

- 至少完成 3 组真实样本手工验证。
- 相同输入重复执行时，若生产环境配置的是实时模型，结果不能表现为固定模板式完全一致。

### 阻塞项 6：旧链路只能兼容保留，不能继续主导上线口径

- [ ] 旧 `/tasks`、`/knowledge` 若仍在仓库中，只作为兼容或内部过渡，不作为正式对外入口。
- [ ] README、实施文档、测试口径、演示口径都统一使用当前商品内容主链描述。

通过标准：

- 新同事或测试人员只看文档就会走正式商品内容主链，不会被旧链路带偏。

## 四、AI 与 Provider 闸门

### 阻塞项 7：登录必须是真实可用的

- [ ] 上线环境 `/auth/config` 返回的认证模式是明确的。
- [ ] 如果走密码登录，上线环境必须真实配置 `AUTH_LOGIN_USERNAME`、`AUTH_LOGIN_PASSWORD`、`AUTH_SECRET_KEY`。
- [ ] 用户可以从正式页面完成登录并进入工作台。

通过标准：

- 演示当天不需要临时改代码切登录方式。
- 不依赖本地开发绕过。

### 阻塞项 8：生成 Provider 必须明确是“真模型”还是“演示回退”，不能糊涂

- [ ] 上线环境明确设置 `TASK_GENERATION_PROVIDER`。
- [ ] 如果上线口径是“真实 AI 生成”，则必须使用真实 Provider，例如 `deepseek`，并配置 `DEEPSEEK_API_KEY`。
- [ ] 不能在用户不知情的情况下用任何固定保底结果冒充正式演示效果。

通过标准：

- 上线前能说清楚：这次演示跑的是哪一个模型、哪一个 provider。
- 如果是回退模式，也必须明确标注为非正式 AI 效果演示。

### 阻塞项 9：检索画像 Provider 必须做明确决策

- [ ] 上线环境明确设置 `RETRIEVAL_PROFILE_PROVIDER`。
- [ ] 如果打算演示真实 AI 驱动的资料利用，就要显式切到真实 provider，并确保失败时直接暴露错误而不是回退到固定画像。

通过标准：

- 生成链和检索画像链分别是什么模式，团队内部没有歧义。

### 阻塞项 10：资料底座必须真实存在

- [ ] 默认电商资料种子已写入并能在运行环境中被索引。
- [ ] 资料底座至少覆盖当前正式方案要求的最小类别。
- [ ] 生成结果里能看到真实的参考依据或命中说明。

通过标准：

- 不是“只有模型在瞎写”，而是“模型结合了当前项目内置资料在生成”。

## 五、验证闸门

### 阻塞项 11：仓库统一校验必须通过

- [ ] 运行 `powershell -ExecutionPolicy Bypass -File scripts/qa/verify.ps1 -Scope all`
- [ ] 校验结果无阻塞失败。

通过标准：

- 不允许跳过统一校验直接说“可以上线”。

### 阻塞项 12：必须做一次真实浏览器正式流验证

- [ ] 用正式入口地址打开首页。
- [ ] 进入工作台。
- [ ] 完成登录。
- [ ] 提交真实商品信息和任务描述。
- [ ] 等待生成完成。
- [ ] 检查结果区真实渲染。
- [ ] 发起导出。
- [ ] 下载导出文件并确认内容可读。

通过标准：

- 这套流程必须在“准备上线的环境”里重跑一遍，不是只在本地开发环境通过。

### 阻塞项 13：至少保留一份正式验收证据

- [ ] 保留 1 份成功导出的真实产物文件。
- [ ] 保留 1 份真实浏览器验证记录。
- [ ] 保留 1 份统一校验结果记录。

通过标准：

- 上线结论有证据，不靠口头描述。

## 六、部署闸门

### 阻塞项 14：必须先选定部署路径，不能边上线边决定

推荐的 Phase 1 可演示上线路径：

- Web：`Vercel`
- API：`Railway`
- 数据与托管能力：按当前仓库实际选择，若沿用文档建议，可配 `Supabase`

- [ ] 已明确本次上线采用哪条部署路径。
- [ ] 已明确 Web 域名、API 域名、运行环境变量注入方式。
- [ ] 正式验收访问地址不是 `file://`、`localhost` 或 `127.0.0.1`。

通过标准：

- 演示当天不依赖本地电脑临时起服务。
- 用户或甲方访问的是部署后的真实地址，不是你自己机器上的本地页面。

### 阻塞项 15：如果坚持用 compose 生产编排，必须先补掉当前已知风险

仓库当前已经明确写了：`infra/docker-compose.prod.yml` 现在只能算“生产意图配置”，不能算“已验证完成的生产收口配置”。

- [ ] 只有在确认端口暴露问题已收口后，才允许把 compose prod 当正式上线方案。
- [ ] 如果没有补完这部分，就不要把 compose prod 说成正式生产部署方案。

通过标准：

- 二选一：
- 走推荐演示部署路径。
- 或者先完成 compose prod 的安全与暴露收口，再上线。

### 阻塞项 16：部署后的访问路径必须正确

- [ ] 前端 `VITE_API_BASE_URL` 指向上线 API。
- [ ] 如果仍使用 Bearer Token 方案，则 `VITE_API_ACCESS_TOKEN` 与后端要求一致。
- [ ] 首页、工作台、登录、生成、导出全都走上线环境真实域名，不混用本地地址。
- [ ] API 已允许正式前端域名跨域访问，不能只放行本地 `localhost` 开发域名。

通过标准：

- 页面请求里不再出现 `localhost`、`127.0.0.1` 这类本地开发地址。

## 七、运行环境闸门

### 阻塞项 17：认证与模型环境变量必须一次配齐

- [ ] `AUTH_LOGIN_USERNAME`
- [ ] `AUTH_LOGIN_PASSWORD`
- [ ] `AUTH_SECRET_KEY`
- [ ] `TASK_GENERATION_PROVIDER`
- [ ] `RETRIEVAL_PROFILE_PROVIDER`
- [ ] `DEEPSEEK_API_KEY`（如果使用 DeepSeek）
- [ ] `VITE_API_BASE_URL`

通过标准：

- 不靠上线后手动补变量救火。

### 阻塞项 18：基础健康检查必须通过

- [ ] `/health` 可访问并返回正常结果。
- [ ] API 日志没有启动即报错。
- [ ] 导出目录可写。
- [ ] Web 部署地址可从外部浏览器直接访问，不依赖本地文件打开。

通过标准：

- 服务启动后，先做健康检查，再做业务验证。

### 阻塞项 19：导出产物链必须可用

- [ ] 导出文件实际写入运行时目录。
- [ ] 导出文件下载接口可用。
- [ ] 下载后的文件内容和页面结果一致，没有空文件、坏文件、错文件。
- [ ] 如果使用独立 worker 处理导出，则 API 与 worker 之间必须共享导出产物存储；不能各写各的本地磁盘。

通过标准：

- 导出不是“按钮亮了”，而是真把文件交付出来了。

---

## 八、上线后最低运维闸门

### 阻塞项 20：至少具备最小可恢复能力

- [ ] 知道如何重启 Web。
- [ ] 知道如何重启 API。
- [ ] 知道如何查看 API 错误日志。
- [ ] 知道导出失败时先看哪几处。

通过标准：

- 演示期间出错，不会因为没人知道去哪里看而全盘失控。

### 阻塞项 21：至少具备最小回退口径

- [ ] 如果真实模型调用异常，团队知道是暂停演示、切备用环境，还是明确降级说明。
- [ ] 如果导出失败，团队知道是否允许只演示页面结果，不承诺导出。

通过标准：

- 每种常见故障都有一句清楚的现场处理口径。

## 九、最终上线判定

下面 5 条必须同时满足，才允许上线：

- [ ] 正式界面已收口，只剩首页和工作台两层。
- [ ] 正式主链已跑通，登录、生成、导出全部真实可用。
- [ ] AI provider 与检索 provider 的上线模式已明确，不存在误报。
- [ ] 统一校验和真实浏览器正式流都已通过。
- [ ] 部署路径、环境变量、健康检查、外部可访问地址和最小运维方案都已完成。

只要上面还有任意一条没有打勾，就不允许上线。

## 十、建议的上线执行顺序

按这个顺序执行，最不容易漏：

1. 先锁定本次上线口径，只认 `Phase 1 可演示上线`。
2. 再锁定部署路径，默认优先 `Vercel + Railway`。
3. 配齐认证、模型、前端接口环境变量。
4. 跑统一校验 `verify.ps1 -Scope all`。
5. 在准备上线的环境里走一遍真实浏览器正式流。
6. 留存导出产物和验证证据。
7. 最后再做上线判定。

## 十一、当前这份清单和仓库现状的关系

结合当前仓库现状，可以直接下结论：

- 当前项目已经有正式商品内容主链，不是空壳。
- 但“可以本地跑通”不等于“已经满足上线闸门”。
- 只有把这份清单里的阻塞项逐项打勾，才可以对外进入正式演示上线。
- 如果你要的是“正式商用上线”，那不是这份清单的口径，必须另起一份更重的生产级清单。
